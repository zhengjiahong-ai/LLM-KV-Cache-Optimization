## 1. PagedAttention / vLLM：分页块管理与实验载体（L0）

### 1.1 统一精读模板

| 字段 | 内容 |
| --- | --- |
| **研究问题** | 连续内存分配造成内部/外部碎片与重复存储，限制批大小和吞吐。 |
| **系统上下文与负载** | 单机 GPU serving；OPT/LLaMA 系列；ShareGPT、Alpaca、翻译、并行采样和 beam search 等负载。 |
| **主要决策层** | **L0 内存布局与块管理**。论文提供分页与共享基础，不定义通用的物理 victim 排序策略。 |
| **核心机制** | 将 KV Cache 切成固定大小逻辑块，通过 block table 映射到非连续物理 Block；按需增长；跨请求共享，并通过 Copy-on-Write 处理写入分叉。 |
| **信号与元数据** | Block table、内容/前缀哈希、引用状态 ref_cnt。 |
| **决策粒度** | 存储与分配以固定大小 Block 为单位；论文讨论的抢占恢复包含序列级 all-or-nothing 处理。 |
| **信息需求** | 不需要 Agent 工作流或工具调用元数据。 |
| **评估方法** | 与 FasterTransformer、Orca 等连续分配方案比较吞吐；分析块大小；分解 recomputation 与 swapping 开销。 |
| **论文报告结果** | 论文报告传统系统的实际 token states 仅占 KV 内存的约 **20.4%–38.2%**，并报告相对当时 SOTA 的 **2–4×** 吞吐改善；重算开销与 swapping 的相对大小依赖具体块大小和硬件条件。 |
| **局限与范围** | 分页解决布局、碎片和共享问题，不等于提出按候选 Block 重算损失排序的算法。序列抢占/恢复也不能直接当作当前 vLLM GPU APC 的物理驱逐规则。 |
| **与本项目的关系** | 提供 vLLM 0.27.1 GPU APC 的存储与共享载体。本项目不修改 PagedAttention 内核、BlockPool 或 Native 所有权路径。 |

## 2. ARC：新近度、频率与自适应空间配比（L1）

### 2.1 统一精读模板

| 字段 | 内容 |
| --- | --- |
| **研究问题** | 仅依赖 LRU 新近度可能无法处理文档 QA 热点与多轮对话时间局部性混合的负载，导致不同工作负载相互冲刷缓存。 |
| **系统上下文与负载** | vLLM 内实现；Qwen3-14B、单张 H100 PCIe 80 GB；KV Block size 为 16 tokens；使用 QuALITY、WikiQA、Zipf 指数 1.0 合成负载及真实多轮对话 trace。 |
| **主要决策层** | **L1 物理驱逐与队列空间配比**。 |
| **核心机制** | T1/T2 分别维护近期访问和重复访问的驻留项，B1/B2 保存被驱逐项的 ghost metadata；ghost hit 反馈调整两类队列的目标容量，重复命中可晋升至频繁队列。 |
| **信号与元数据** | Recency、frequency、ghost hit。 |
| **决策粒度** | 物理 Block 与队列空间配额。 |
| **信息需求** | 不需要外部 Agent 工作流信息。 |
| **评估方法** | 对比 LRU、固定双队列 DBL 与 ARC；报告命中率、TTFT 随缓存容量变化，并分析不同 batch size 与队列配额变化。 |
| **论文报告结果** | QuALITY 容量扫描中，作者报告相对 LRU 的命中率改善约 **1.2%–10.8%**、平均 TTFT 下降约 **2.0%–12.6%**；WikiQA 命中率改善约 **2.5%–7.8%**。真实多轮负载的收益较小，约为命中率 **+2.1%**、TTFT **−2.0%**。 |

| **与本项目的关系** | 是 Block 替换与访问历史的机制对照，不是当前实验基线。它提醒我们：增加信号或自适应机制本身并不能证明成本感知的独立价值。 |

## 3. RLT + LBGR：随机前缀替换与学习型路由（L1 + L4）

### 3.1 统一精读模板

| 字段 | 内容 |
| --- | --- |
| **研究问题** | 在动态在线查询到达下，前缀树叶子替换可能受请求顺序影响；多 worker serving 还需要权衡前缀亲和与排队负载。 |
| **系统上下文与负载** | SGLang；Llama-3.1-8B 使用 10×L40，Llama-3.1-70B 与 Mixtral 8×7B 使用 4×H200；1–10 workers（默认 4）；负载包括 Generated Shared Prefix、ShareGPT/UltraChat、Loogle；随机到达和 worst-case round-robin 到达；输出长度 4–128 tokens。 |
| **主要决策层** | **L1 前缀叶子替换（RLT）+ L4 请求路由（LBGR）**。 |
| **核心机制** | RLT 在缓存压力下从未标记的叶子 token 中随机选择 victim；LBGR 通过在线学习估计服务时间、队列负载与残差校正后的请求时延，选择 worker。两者作用对象不同。 |
| **信号与元数据** | RLT 使用叶子标记与随机性；LBGR 使用服务时延、队列负载和残差校正。 |
| **决策粒度** | RLT 为 radix tree 叶子 token；LBGR 为请求到 worker 的路由。 |
| **信息需求** | 需要论文设定中的前缀共享结构和到达过程；不要求预先提供 Agent workflow graph。 |
| **评估方法** | 理论竞争比分析与多 benchmark 实验；报告命中率、P50/P95 延迟、TTFT、吞吐及驱逐/路由开销。 |
| **论文报告结果** | 在论文模型下，Leaf-LRU 最坏竞争比为 O(n)，RLT 改善为 O(log n)。论文实验报告的最高改善值包括命中率约 **6.92×**、时延最高降低约 **11.96×**、TTFT 最高降低约 **14.06×**、吞吐最高提升约 **77.4%**；这些是跨条件的最高报告值，不应理解为同一负载上的统一收益。 |
| **局限与范围** | RLT 的 victim 选择本身是随机的，不估计单个候选的重算成本；LBGR 的成本估计用于路由而不是逐块驱逐。联合结果不能归因成 RLT 单组件收益。 |
| **与本项目的关系** | 是理论与机制参照，不复现为基线。它说明优于 LRU 的结果不必然来自成本模型，因此本项目必须依赖冻结对照与可归因证据判断成本信号的独立价值。 |

## 4. Continuum：程序感知 TTL、保护与调度（L2 + L3 + L4）

### 4.1 统一精读模板

| 字段 | 内容 |
| --- | --- |
| **研究问题** | Agent 执行工具调用时 LLM 暂停；若 turn 结束即回收 KV，后续轮次可能需要重算并重新排队，产生缓存重建和调度气泡。 |
| **系统上下文与负载** | 论文扩展 vLLM；Llama-3.1-8B/70B、Gemma-3-12B，另在真实 SWE-agent 场景讨论 GLM-4.5；A100、H100、B200；SWE-Bench、BFCL V4 Web Search、OpenHands；Poisson 到达及真实 Agent 测试。主要论文对照包括 vanilla vLLM 0.10.2、vLLM + LMCache、Autellix、InferCept、SGLang 与 NVIDIA Dynamo。 |

| **与本项目的关系** | Phase 1B 适配其 program/session identity、请求间隔历史、Dynamic TTL、软保护和调度基础；本项目是 vLLM 0.27.1 上的 Continuum-style adaptation，不是源码级精确复现。 |

### 4.2 机制细节与适配边界

1. **TTL 目标函数。** 论文枚举 S[f] 中已观测的服务端请求间隔，并将 τ=0 加入候选，最大化 P(τ,f) × (T·η + Prefill-Reload(r)) − τ。
2. **请求间隔样本。** P(τ,f) 使用服务端相邻请求间隔 t_arrive(i+1) − t_finish(i)。论文 §5.1 将其记录为本次工具调用执行时长的估计样本；项目中的 server_inter_request_gap 属于这一统计量。
3. **排队与记忆度。** T 表示被逐出请求经历的 queueing delay 滑动窗口平均；η 为 −Corr(k, N−k)，允许为负值，不能未经依据裁剪到 [0,1]。
4. **重算/载入代价。** Prefill-Reload(r) 来自离线硬件/模型 profiling，并拟合不同 chunk size 下的 prefill 时间；不能将它理解为论文在每次 victim 选择时实时运行一次完整 profiling。
5. **冷启动。** 论文在样本量不足时依次使用默认估计、全局样本和按工具类型样本；样本阈值与回退层级是 TTL 估计器的一部分。
6. **论文的压力释放与项目 A0 不同。** Continuum §5.2 的死锁预防按 latest program arrival time 迭代解除保护；项目 A0 冻结的是项目侧适配顺序，不能把二者写成同一规则。

### 4.3 项目 A0 的完整冻结顺序

项目 A0 的 Entry Release 顺序是独立于论文 §5.2 死锁处理规则的项目适配。对当前待释放 Entry e，排序键为：

\[
\left(
deadline(e),
\min_{b \in NewlyEligible(e)} native\_lru\_rank(b),
identity(e)
\right)
\]

其中 NewlyEligible(e) 是在当前已释放集合与资格状态下，**仅因释放 e 而新获得物理驱逐资格的 Block 集合**；第二键取这些 Block 的最小 Native LRU rank。若集合为空，第二键按正无穷处理。第三键是 Entry identity 的确定性排序键。

因此，A0 不是只有 deadline-first：完整顺序是 **Entry deadline → newly eligible Blocks 的 minimum Native LRU rank → deterministic Entry identity**。它改变的是 Entry 释放顺序；A0 的物理 Block victim selection 仍使用 Native LRU。实现依据为 pressure.py::_release_sort_key()，冻结边界见 docs/baseline-freeze.md。

## 5. SAGA：工作流感知保留、驱逐与集群协调（L1 + L2 + L4 + L6）

### 5.1 统一精读模板

| 字段 | 内容 |
| --- | --- |
| **研究问题** | 请求级调度忽视 Agent 工作流原子性，导致工具调用间隙 KV 重建、缓存亲和性损失和多租户资源竞争。 |
| **系统上下文与负载** | 8 节点 × 8 A100-80GB，共 64 GPU；Ray + gRPC；vLLM 0.6.0 扩展；Llama-3-70B-Instruct TP=4；SWE-bench 500 verified tasks、WebArena 812 tasks，以及 BurstGPT 衍生的 10 租户负载。SWE-bench/WebArena 按约 8 tasks/min 的 Poisson 到达计划重放，单租户主实验重复 10 次。 |
| **主要决策层** | **L4 工作流调度 + L2 TTL + L1 WA-LRU 驱逐排序 + L6 集群协调**。 |
| **核心机制** | AEG 由框架 hint 或 trace pattern inference 获得；工具调用感知 TTL 根据工具时长分位数与显存压力调整；WA-LRU 使用预测复用概率、新近度和缓存大小排序；session-affinity batching、work stealing 与 Agent Fair Share 负责集群级协调。 |
| **信号与元数据** | 工具类型历史时长分位数、显存压力、AEG 预测复用概率、recency、Block 大小。 |
| **决策粒度** | Workflow task、Agent session、KV Block 和 worker/cluster。 |
| **信息需求** | 需要 AEG 或历史 trace 推断模块；完整系统还需要集群路由与协调。 |
| **评估方法** | TCT、GPU memory utilization、throughput、SLO、与 Bélády 离线最优的接近程度、多租户公平性、系统开销和逐组件消融。 |
| **论文报告结果** | Table 2 的离线竞争比（越接近 1 越好）为：Standard LRU 在 SWE-bench/WebArena/Mean 上 **2.84/2.12/2.48**；LRU + Prefix 为 **1.97/1.74/1.86**；WA-LRU 为 **1.31/1.28/1.30**。Table 3 中完整 SAGA 相对 vLLM + APC v0.15.1 的任务完成时间比为 SWE-bench **1.73×±0.11**、WebArena **1.55×±0.09**；相对 vLLM 0.6.0 分别为 **3.01×±0.16** 与 **2.17×**。 |
| **局限与范围** | 结果包含 TTL、驱逐、调度和集群协调，不能将端到端加速全部归因于 WA-LRU。AEG 与分布式系统超出当前 Phase 3 的组件比较范围。Table 2 的竞争比不是时延加速比。 |
| **与本项目的关系** | 是工作流感知管理的设计参照，不是当前实验臂。它支持区分保留、驱逐和调度的不同作用层级，但不能替代对本项目单一决策层的独立 Native 比较。 |

### 5.2 关键结果与消融口径

- **Table 2：** 与 Bélády 离线最优的接近程度，1.0 表示最优。引用时必须按列使用，不能把 LRU + Prefix 的 Mean 1.86 当成 SWE-bench 数字。
- **Table 3：** 10 次重复的端到端 TCT 比较。SAGA 的绝对 TCT 为约 203.4s，GPU memory utilization 约 71.3%；vLLM 0.6.0 的对应值约 612.3s、42.1%。这些数字属于该论文的 64×A100 系统与负载。

## 7. CacheWise：Coding Agent 负载、工具元数据与预测式驱逐（L1 + L4）

### 7.1 统一精读模板

| 字段 | 内容 |
| --- | --- |
| **研究问题** | Coding Agent 的长时闭环会话在 LLM 请求与外部工具调用间交替，长前缀反复提交，缓存复用与准入/驱逐相互影响。 |
| **系统上下文与负载** | vLLM 原型；Qwen2.5-Coder-32B-Instruct；2×H200（TP=2）、AMD EPYC 9534 64 核；自采 CATraces，80% 会话用于离线训练，剩余会话评估；并发会话数 N≤10 与 N>10 分层。 |

| **核心机制** | Prefix-aware scheduling 按请求与 XPU 常驻 KV 的重叠度安排准入；预测式驱逐为 KV Block 附加工具类型、参数与已等待时间等会话元数据，估计未来再次使用时间并排序。工具参数通过 TF-IDF 表征和 KMeans 聚类，以处理同名工具不同参数/环境下的时长差异；预测堆按 engine iteration 周期性重建。 |
| **信号与元数据** | tool_name、tool_args、已等待时间、历史工具执行时长分布、常驻前缀重叠。 |
| **决策粒度** | 请求准入与会话关联的 KV Block。 |
| **信息需求** | 需要 Agent 框架暴露工具调用类型与参数等元数据，并依赖 CATraces 的训练分布。 |
| **评估方法** | 确定性重放 CATraces；比较 vLLM Block LRU + FCFS、InferCept moving-average eviction；拆分 prefix-aware scheduling 与 predictive eviction 消融。会话完成时间按论文 §6.1 的口径计算，排除工具执行时间。 |
| **论文报告结果** | 完整 CacheWise 在 N>10 时相对 vLLM/InferCept 报告约 **2.7×–3.5×** 的会话完成时间改善，驱逐次数减少约 **2–2.6×**。在已启用 prefix-aware scheduling 的基础上单独加入预测式驱逐，完成时间改善约 **1.7×–2×**；单独的 prefix-aware scheduling 也有显著增益。 |
| **局限与范围** | 端到端 3.5× 是准入调度与驱逐的合成效果，不是纯驱逐贡献；论文 §1 的 request completion 与结论的 session completion 用词不完全一致。工具元数据、训练分布与 XPU 容量单位不能直接映射到本项目。 |
| **与本项目的关系** | 是工具元数据驱动复用预测的机制对照。不能据此声称本项目已有相同工具特征消费者；本项目中 ExternalToolDurationHistory 的实际读取状态须以代码审计为准。 |

### 7.2 机制与消融必须分开理解

- **Prefix-aware Request Scheduling：** 根据等待请求与当前 XPU 常驻 KV 的前缀重叠度安排准入，属于 L4。
- **Predictive KVCache Eviction：** 对 tool_name、tool_args、已等待时间等特征估计未来复用时机，再为无活跃引用的 Block 排序，属于 L1。
- **预测更新：** 论文通过参数文本聚类缓解同名工具执行时长的多峰分布，并周期性重估预测堆；这是对工具环境与训练样本分布的依赖，不是免费可得的 Native 信号。
- **结果归因：** 完整系统 2.7×–3.5× 包含调度与驱逐；纯驱逐消融约 1.7×–2×，两者不可互换。论文没有直接评估本项目的 Entry Release。

## 8. When Fancy Eviction Fails：复杂替换的反向证据（L1）

### 8.1 统一精读模板

| 字段 | 内容 |
| --- | --- |
| **研究问题** | 传统缓存替换算法能否直接迁移到 Agentic / 对话式 LLM prefix caching；复杂策略是否稳定优于 LRU。 |
| **系统上下文与负载** | FreeInference Trace：327.5K requests、10.5B tokens、7.0 days、34.3% 多轮请求；Chutes Trace：515.8K requests、9.7B tokens、130.9 days、26.1% 多轮请求；合计超过 20B processed tokens。实验覆盖 Qwen3-Coder-30B、H200 48 GiB、B200 96 GiB、vLLM，以及自建模拟器和生产 trace replay。 |

| **核心机制** | 比较 14 种在线替换算法，并以 Bélády 离线最优作为 ceiling；进一步分析 quick demotion、compute-aware eviction（包括 partial-node）与 capacity-adaptive eviction granularity（Block-level / Session-level）。 |

| **决策粒度** | Block、partial-node 与 Session-level；这些是 L1 替换粒度，不等于逻辑 Entry 的 unpin 粒度。 |

| **论文报告结果** | 在多数主 trace 与容量点上，LRU 与复杂在线策略表现接近，频率类算法有时更差；但结论并非“LRU 普遍最优”。24 GiB 的 Qwen To-B trace 中，S3-FIFO 与 ARC 的 block hit ratio 为 **0.491**，LRU 为 **0.403**，构成明确反例。 |
| **局限与范围** | 命中率类结果主要来自自建模拟器与 trace replay；Figure 7、8、13 才是论文标注的真实 GPU/vLLM 测量。容量、trace、模型和硬件决定结论适用范围。 |
| **与本项目的关系** | 是保留 Native LRU 强基线的关键反向证据。它要求成本感知策略证明相对 LRU 的增量价值，而不是先验假定复杂策略更好。 |

### 8.2 结构性发现与结果解释

- **Recency 的强预测力：** 活跃会话的前缀复用具有稳定的时间局部性，因此简单 LRU 在不少真实 trace 上表现稳健。
- **Miss cost 非均匀：** 重算代价会随 token 深度和上下文位置变化，不能只用命中/未命中次数完整表达计算损失。
- **Session footprint 重尾：** Figure 10a 报告中位每会话约 45 Blocks，但分布有明显长尾。
- **容量依赖与非单调性：** 部分策略的收益会随容量变化而反转；不能只选一个容量点得出普遍结论。
- **并发度效应：** 固定容量下并发会话增加会改变所有策略的命中表现；容量、并发与 trace 应联合报告。
- **反例纪律：** 24 GiB Qwen To-B 上 S3-FIFO / ARC 的 0.491 高于 LRU 的 0.403，引用时必须同时写出容量与 trace，不得将“LRU 稳健”改写为“LRU 永远最优”。

论文 §3.2 的 14 种在线算法包括 LRU、ARC、Sieve、S3-FIFO、S4-FIFO、LIRS、LHD、LFU、W-TinyLFU、LeCaR、LRB、3LCache、Workload-aware 与 AsymCache。Bélády 是离线 ceiling，不属于 14 种在线算法。

## 9. 使用本附录时的汇报纪律

1. **论文结果不是项目结果。** 所有倍数、命中率和延迟数字必须标注“论文报告”，并保留模型、硬件、负载、baseline 和指标定义。
2. **联合系统结果不能归因给单一组件。** 尤其是 SAGA、KVFlow、CacheWise，必须区分 TTL、驱逐、准入、调度、预取与集群协调。
3. **层级不可混用。** L0 布局、L1 Block victim selection、L2 TTL、L3 Entry protection/release、L4 admission/scheduling、L5 prefetch/offload、L6 workflow coordination 不是同一类决策。
4. **A0 不是论文原始 Continuum 规则。** A0 的 Entry Release 排序是项目冻结适配；其完整键为 deadline、释放后新增资格 Block 的 minimum Native LRU rank、确定性 Entry identity。物理 victim selection 仍为 Native LRU。
5. **LRU 是强基线，不是先验最优。** WFEF 同时包含 LRU 稳健结果与特定容量下的反例；项目结论必须由冻结 Native 配对实验给出。
