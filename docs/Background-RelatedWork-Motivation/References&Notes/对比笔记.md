## 1. 对比的五个维度

所有横向对比统一采用以下五个维度：

| 维度 | 含义 | 为什么重要 |
| --- | --- | --- |
| **D1 作用层级** | 策略改的是内存布局、驱逐决策，还是调度/保留 | 界定相关工作与我们的工作是否在同一层面竞争 |
| **D2 决策信号** | 驱逐/保留决策依据哪些信息（时间戳、频率、成本、工作流图…） | 直接决定策略能否感知"异构成本" |
| **D3 决策时机与粒度** | 何时决策（到期/驱逐时刻）、对什么粒度决策（整会话/块/前缀） | 决定策略的灵活性与误杀风险 |
| **D4 信息需求** | 是否需要先验信息（工具统计、AEG 工作流图、编排器 hint） | 决定策略在真实黑盒场景下的可用性 |
| **D5 评估方式** | 用什么负载与指标验证 | 为我们选择实验指标与作图方式提供依据 |

## 3. 按主题类的成对对比

### 3.1 传统驱逐类：LRU vs. RLT

**共同点**：两者都在缓存压力下选择逐出对象，且不直接用候选块的重算时间排序。

| 对比项 | LRU | RLT |
| --- | --- | --- |
| 选择逻辑 | 按最后访问时间；在前缀树中可采用 Leaf-LRU | 未标记叶子 token 中随机一个 |
| 解决的问题 | 简单的访问历史基线 | 减弱对到达顺序的依赖 |
| 理论竞争比 | RLT 论文在其模型下给出 Leaf-LRU 最坏 \(O(n)\) | 同一模型下为 \(O(\log n)\) |
| 限制 | 不直接估计重算时间 | 随机选择不直接估计候选价值 |

**对我们的意义**：LRU 是我们的 Baseline 1；RLT 说明"比 LRU 好"不一定需要成本模型，因此我们的实验必须证明**收益来自成本信号本身**（消融实验的必要性，见 experiment-plan）。

### 3.2 自适应类：ARC

**与 LRU 的区别**：增加了频率维度与幽灵缓存反馈，能随负载调整新近度/频率的空间配比。

**与本项目方法的区别**（报告 Related Work 需写清）：

- ARC 调的是**两类队列的空间配比**，我们拟调的是**每个块的驱逐优先级**，两者的决策形式不同；
- ARC 的信号仍是"会不会再被访问"，不含"被逐出的代价有多大"；
- ARC 对系统状态（显存压力、排队）无反馈，其"自适应"只针对访问模式。

**可借用的实验方法**：命中率 / TTFT vs. 缓存大小的作图方式（ARC 图 3–5），以及 QuALITY/WikiQA/Zipf/多轮 trace 的负载组合思路。

### 3.3 保留租约类：Continuum vs. SAGA（支撑系统基础与相关工作边界）

两者都解决"Agent 工具调用挂起期缓存被误逐"的问题，都引入 TTL，但设计哲学不同：

| 对比项 | Continuum | SAGA |
| --- | --- | --- |
| TTL 计算依据 | 服务端请求间隔历史（server_inter_request_gap）+ 排队延迟 T + 预填充重算开销 PrefillReload + 轮次记忆度因子 eta | 工具类型历史延迟分位数（如 95%） |
| 显存压力响应 | 显存压力下按策略提前解除部分保护，防止死锁 | 有：压力因子缩短 TTL，高阈值下硬驱逐 |
| 到期后处理 | 达到截止时间或压力下解除保护 | TTL 不提供无限期保护，结合逐出管理 |
| 驱逐侧配套 | 无专门驱逐策略 | WA-LRU 驱逐分数（重用概率 + 新近度 + 大小 + TTL 状态） |
| 信息需求 | 工具调用历史（可在线收集） | AEG 或由历史 trace 推断的工作流 |
| 粒度 | 按程序 / 会话前缀的 KV 缓存保留 / 解除保护 | 工作流任务及其缓存状态 |

**与本项目的关系**：

1. Continuum 的 program/session 生命周期、动态 TTL、软留存与压力释放构成 Phase 1B 项目适配的系统基础；
2. SAGA 的 WA-LRU 是另一种工作流感知逐出设计，可作为相关工作参照，但不是当前 Phase 3 的直接实验臂；
3. Phase 3 研究的是在该 Continuum-style 系统基础上，如何改进逻辑 Entry Release 与物理 Block Victim Selection，不能将其简化为“Continuum 只保留，本项目只驱逐”的互斥关系。

**对 Phase 1B adaptation 的指导**：

- Continuum 的 `CalcTTL`、软保护、解除保护与程序级调度是系统机制参考；
- 项目实现与原论文存在明确适配边界，见 `docs/baseline-freeze.md` 与 `docs/continuum-baseline-implementation.md`；
- 当前 Phase 3 的 A0 是项目侧 Entry Release baseline，不是完整公开 Continuum 系统。

### 3.4 保留指令类：vLLM RFC #37003

来自 `参考文献/关于vLLM的参考文档与网址.md` 的第三份材料：社区提案允许编排器对 token 范围标注**驱逐优先级与生存时间**（retention directives），以解决 Agent 工作流下 LRU 误清会话前缀、引发高昂重算成本的问题。

- **定位**：工程提案而非论文，属于"自顶向下由调用方指定优先级"路线；
- **与我们的关系**：它提供由调用方声明保留优先级的接口；本项目拟根据运行时数据进行候选排序。两者可以互补，但 RFC 不应被当作已验证的性能证据。

## 4. 我们的方法与最接近工作的区分

### 4.1 与 SAGA 的 WA-LRU 对比

WA-LRU 是相关工作中的工作流感知逐出策略。当前 Phase 3 并未将 SAGA/WA-LRU 作为直接实验臂；因此只能比较机制设计与信息需求，不能据本项目 campaign 声称优于 WA-LRU。

本项目当前实验的策略输入与决策语义以 Protocol v4 为准，不再用早期“所有候选块统一在线打分”的概括替代 A1/A2/A3/E0 的分层定义。

### 4.2 Continuum-style adaptation 与当前优化研究的关系

| 层次 | Continuum-style 系统基础 | 当前 Phase 3 研究 |
| --- | --- | --- |
| 生命周期 | Program / Session identity、工具间隔历史 | 作为共同系统上下文保持冻结 |
| Retention | Dynamic TTL、软保护、lazy expiry | 记录机制证据；无 Static-TTL 对照臂 |
| Entry Release | 压力下解除逻辑条目保护 | A0 baseline；A1/A3/E0 改变此层决策；N0 为 no-forced-release control |
| Physical Block Victim Selection | 交由 Native vLLM 物理淘汰路径 | A0/A1/A3/E0 使用 Native LRU；A2 改变物理 victim selector |
| Scheduling | Phase 1B narrow admission-order adaptation | Phase 3 全部固定 Native scheduler，不估计调度性能效应 |

因此不应再把两者写成互斥的“TTL 保留 vs. 逐出排序”路线；当前研究是在已适配的 Continuum-style 系统中分别研究两个缓存决策层。

### 4.3 与 RLT 的区别

RLT 的理论结论来自特定前缀共享与到达顺序模型，不能直接推出其他负载中的表现。RLT 不是当前 Phase 3 注册实验臂；Phase 3 不包含“仅重算成本 / 仅复用信号 / 完整模型”的通用消融矩阵。相关讨论仅作为文献背景，不应写成当前实验承诺。
