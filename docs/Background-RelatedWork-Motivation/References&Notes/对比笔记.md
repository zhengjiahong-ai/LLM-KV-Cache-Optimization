## 1. 对比的五个维度

所有横向对比统一采用以下五个维度：

| 维度 | 含义 | 为什么重要 |
| --- | --- | --- |
| **D1 作用层级** | 策略改的是内存布局、保留/释放、驱逐决策，还是调度 | 界定相关工作与我们的工作是否在同一层面竞争 |
| **D2 决策信号** | 决策依据哪些信息（时间戳、频率、工作流距离、工具元数据…） | 直接决定策略能感知什么 |
| **D3 决策时机与粒度** | 何时决策（到期/压力/驱逐时刻）、对什么粒度决策（Entry/会话/块/前缀） | 决定策略的灵活性与误杀风险 |
| **D4 信息需求** | 是否需要先验信息（工具统计、AEG 工作流图、编排器 hint） | 决定策略在真实黑盒场景下的可用性 |
| **D5 评估方式** | 用什么负载与指标验证 | 为我们选择实验指标与作图方式提供依据 |

## 3. 按主题类的成对对比

### 3.1 传统驱逐类：LRU vs. RLT

**共同点**：两者都在缓存压力下选择逐出对象，且不直接用候选块的重算时间排序。

| 对比项 | LRU | RLT |
| --- | --- | --- |
| 选择逻辑 | 按最后访问时间；在前缀树中可采用 Leaf-LRU | 未标记叶子 token 中随机一个 |
| 解决的问题 | 简单的访问历史基线 | 减弱对到达顺序的依赖 |
| 理论竞争比 | RLT 论文在其模型下给出 Leaf-LRU 最坏 \(O(n)\) | 同一模型下为 \(O(\log n)\) |
| 限制 | 不直接估计重算时间 | 随机选择不直接估计候选价值 |

**对我们的意义**：LRU 构成 Baseline 1 的 Block 层规则（Baseline 1 口径见 [`../../baseline-freeze.md`](../../baseline-freeze.md)）；RLT 说明"比 LRU 好"不一定需要成本模型，因此我们的实验必须证明**收益来自成本信号本身**（消融实验的必要性，见 experiment-plan）。

### 3.2 自适应类：ARC

**与 LRU 的区别**：增加了频率维度与幽灵缓存反馈，能随负载调整新近度/频率的空间配比。

**与本项目方法的区别**（报告 Related Work 需写清）：

- ARC 调的是**两类队列的空间配比**，我们拟调的是**每个块的驱逐优先级**，两者的决策形式不同；
- ARC 的信号仍是"会不会再被访问"，不含"被逐出的代价有多大"；
- ARC 对系统状态（显存压力、排队）无反馈，其"自适应"只针对访问模式。

**可借用的实验方法**：命中率 / TTFT vs. 缓存大小的作图方式（ARC 图 3–5），以及 QuALITY/WikiQA/Zipf/多轮 trace 的负载组合思路。

### 3.3 保留租约类：Continuum vs. SAGA（重点，支撑 Baseline 2 的设计取舍）

两者都解决"Agent 工具调用挂起期缓存被误逐"的问题，都引入 TTL，但设计哲学不同：

| 对比项 | Continuum | SAGA |
| --- | --- | --- |
| TTL 计算依据 | 服务端请求间隔历史（server_inter_request_gap）+ 排队延迟 T + 预填充重算开销 PrefillReload + 轮次记忆度因子 eta | 工具类型历史延迟分位数（如 95%） |
| 显存压力响应 | 显存压力下按策略提前解除部分保护，防止死锁 | 有：压力因子缩短 TTL，高阈值下硬驱逐 |
| 到期后处理 | 达到截止时间或压力下解除保护 | TTL 不提供无限期保护，结合逐出管理 |
| 驱逐侧配套 | 无专门驱逐策略 | WA-LRU 驱逐分数（重用概率 + 新近度 + 大小 + TTL 状态） |
| 信息需求 | 工具调用历史（可在线收集） | AEG 或由历史 trace 推断的工作流 |
| 粒度 | 按程序 / 会话前缀的 KV 缓存保留 / 解除保护 | 工作流任务及其缓存状态 |

**与本项目的主要差别**：

1. Continuum 的主要输出是 TTL；SAGA 除 TTL 外还提供基于 AEG 的逐出排序；
2. Continuum 的 TTL 计算考虑重算/重载和排队影响，SAGA 的 WA-LRU 不直接以候选块的重算时间排序；
3. 本项目拟在块级候选之间比较成本和复用信号。该差别是研究假设，不应预设为性能优势。

**对 Baseline 2 实现的直接指导**：

- 复现 Continuum 的 `CalcTTL` + 软保护 / 解除保护 + 优先级调度（指南见 `论文总结.md` §4.2）；
- 不将 SAGA 的 TTL 或 WA-LRU 机制并入 Continuum 基线；
- 基线不退化为普通 LRU（experiment-plan 的硬性要求）。

### 3.4 保留指令类：vLLM RFC #37003

来自 `参考文献/关于vLLM的参考文档与网址.md` 的第三份材料：社区提案允许编排器对 token 范围标注**驱逐优先级与生存时间**（retention directives），以解决 Agent 工作流下 LRU 误清会话前缀、引发高昂重算成本的问题。

- **定位**：工程提案而非论文，属于"自顶向下由调用方指定优先级"路线；
- **与我们的关系**：它提供由调用方声明保留优先级的接口；本项目研究由系统在线估计并排序。两者可以互补。
- **证据等级**：这是 RFC / 工程接口提案，**不是同行评审论文，不得作为性能收益证据**。仓库参考笔记记载其标题为 "Context-Aware KV-Cache Retention API (Prioritized Evictions)" 且当时为 Open 状态。

## 4. 四个方向与最接近工作的区分

不按"我们的方法 vs 某篇论文"组织，而按四个研究方向分别指出最接近的工作与必须守住的边界。

### 4.1 Block Idea 1（介入门槛与 Native-LRU 回退）

| 最接近的工作 | 可借鉴之处 | 必须守住的边界 |
| --- | --- | --- |
| *When Fancy Eviction Fails* | 提供"复杂策略未必优于 LRU"的系统性反向证据与真实生产 trace 规模 | 论文结论不能移植为本项目结论；不得仅据标题推断其方法 |
| vLLM 原生 LRU / A2 已有回退路径 | 给出真实基线的候选约束与排序语义 | 离线 `native_selection()` / `native_lru_order()` 只按 `native_rank` 排序、**不含 tier 约束**，不是 A0 基线 |

### 4.2 Block Idea 2（Continuum 中间信号）

| 最接近的工作 | 可借鉴之处 | 必须守住的边界 |
| --- | --- | --- |
| Continuum | 中间信号的来源与生命周期：请求间隔、排队延迟、`eta`、预填充重算开销 | 这些信号当前只进 `estimate_ttl()`，**只有 `deadline_timestamp` 到达 Block 层** |
| CacheWise | 工具调用元数据可作为复用预测信号 | **不得**假设其信号已被本仓库实现；本项目 `ExternalToolDurationHistory` 只写不读 |
| KVFlow | 提供与在线信号不同来源的信号族（工作流距离） | 依赖工作流结构，**不能默认在驱逐时刻可用**；不得把论文加速比当作预期收益 |

### 4.3 Entry Idea 3（unpin 排序）

| 最接近的工作 | 可借鉴之处 | 必须守住的边界 |
| --- | --- | --- |
| Continuum 压力释放（冻结 A0 顺序） | 给出被冻结的基线顺序与 newly-eligible Block 计算 | A0 已消费 `native_lru_rank`，headroom 可能很小；**不得**把它说成随手实现的启发式 |
| SAGA 的显存压力缩放 TTL | 说明保留时长、内存压力与驱逐排序可分开设计 | SAGA 需要 AEG，本项目不接入 |
| A1 的 54/54 复现 | 直接的反向警示：更丰富的排序可能退化成简单规则 | 必报 pairwise ordering agreement 与 rank correlation，不能只报 outcome 差异 |

### 4.4 Entry Idea 4（unpin 粒度）

| 最接近的工作 | 可借鉴之处 | 必须守住的边界 |
| --- | --- | --- |
| *When Fancy Eviction Fails* §5.2/§5.3 | compute-aware eviction 与 block-level vs session-level 粒度的权衡 | 论文的部分粒度讨论**不等于**本项目的 partial-tail unpin |
| KVFlow §3.1/§3.2 | 树状结构中共享前缀的保留方式（共享节点取最保守优先级） | 其依赖工作流结构；且共享节点保留是**驱逐优先级**问题，不是保护粒度问题 |
| vLLM RFC #37003 | token 范围保留指令的接口先例 | RFC 不是性能证据，且其状态未经本次核验 |

### 4.5 一个跨方向的共同约束

*When Fancy Eviction Fails* 对四个方向提出同一个要求：**复杂不等于更好**。因此每个方向都必须回答"相对简单规则的实际改进是什么"，而不是"规则之间是否存在差异"。
