## 1. 为什么必须分成三张表

把"研究问题、系统上下文、决策机制、与本项目的关系"塞进一张表，会诱发两类错误：

1. **跨层比性能**——把只改 TTL 的系统与只改驱逐算法的论文放在同一行比命中率；
2. **把不可移植的结论当成结论**——把论文在 64 卡集群、Poisson 合成到达下得到的加速比，当成本项目在单卡真实 APC 下的预期。

因此本文拆成三张表，各有各的用途：

| 表 | 内容 | 用途 | 禁止用法 |
| --- | --- | --- | --- |
| **A. 研究问题与系统上下文** | 每篇工作面对什么问题、跑在什么系统与负载上 | 判断"是否在同一层面竞争" | **不得**在此表放任何性能数字 |
| **B. 决策层·机制·信号·粒度·信息需求** | 每篇工作改哪一层、用什么信号、对什么粒度决策、需要什么外部信息 | 判断"信号与粒度是否可迁移到本项目" | **不得**在此表放任何性能数字 |
| **C. 相关性与不可移植结论** | 每篇工作对本项目哪一层有参考价值、哪些结论不能直接搬 | 写 Related Work 的"差异"段落 | **不得**把"论文报告结果"写成"本项目结论" |

### 5.3 必须同时声明的三个"不可比"来源

1. **负载不可比**：SAGA/KVFlow 用合成或框架生成的工作流，CacheWise 用自采 coding trace，Continuum 用 GPT-5 生成 + Poisson 到达，WFEF 用两条生产 trace。**都不等于本项目的 W1-A/W1-C 真实 SWE-bench Verified Agent 轨迹**（且 W1-A 十个任务全部来自 Astropy、9/10 在 50 步上限处右删失）。
2. **系统不可比**：后端从 vLLM 0.6.0 到 0.15.1 到 0.27.1，还有 SGLang v0.4.4；单卡到 64 卡集群；有的开启 APC，有的没有。
3. **指标不可比**：命中率 / TTFT / TCT / goodput / compute-savings ratio / 与 Bélády 的接近度，是五种不同的量。**特别是"与 Bélády 最优的接近程度"（SAGA Table 2）绝不能与时延加速比（SAGA Table 3）混用。**

## 6. 重点成对对比

### 6.1 Continuum vs. SAGA —— 为什么不是"另一种 LRU 变体"，也不是一回事

两者都解决"Agent 工具调用挂起期缓存被误逐"的问题，都引入 TTL，但**决策层、系统形态、粒度与信息需求都不同**：

| 对比项 | Continuum | SAGA |
| --- | --- | --- |
| 决策层 | **L2 TTL 为主** + L3 释放 + L4 调度；**无 L1 驱逐策略** | **L4 调度 + L2 TTL + L1 WA-LRU + L6 集群协调**，四层叠加 |
| 系统形态 | 单机/少卡 vLLM 调度器扩展（~1k 行 Python） | **分布式集群调度器**（Ray + gRPC + 8.5K 行 Python + 1.2K 行 C++/CUDA） |
| TTL 计算依据 | inter-request interval 经验 CDF + 排队延迟 T + 预填充重算开销 + `η = −Corr(k, N−k)` | 工具类型历史时延 **p 分位数（默认 95%）** × 显存压力因子，上限 `TTL_max = 300s` |
| 显存压力响应 | 调度失败时按 **latest program arrival** 迭代解除保护（死锁预防） | 压力因子**成比例缩短 TTL**；过订阅（>95%）优雅退化为标准 LRU；高阈值硬驱逐 |
| 驱逐侧配套 | **无专门驱逐策略**（交给底层引擎） | **WA-LRU**（AEG 复用概率 + 新近度 + 缓存大小） |
| 信息需求 | 工具调用历史（**可在线收集**）+ 程序身份（客户端提供） | **AEG**：框架 hint 或由历史 trace 做 pattern inference |
| 粒度 | 请求 / 程序前缀条目 | 工作流任务 / agent 会话 / KV 块 |
| 冷启动处理 | 三级层次（`T_default` / 全局记录 / 细粒度），K=100 | EMA 更新分位数；无等价的三级冷启动层次 |

**结论**：Continuum 是**保留时长 + 程序级调度**系统，其输出是 TTL，不是块级排序；SAGA 是**工作流原子调度 + 自带逐出排序**的集群系统。二者**不可互换**：把 SAGA 的 WA-LRU 并进 Continuum 基线会改变 A0 的决策层定义，`docs/baseline-freeze.md` 明确禁止。

**为什么 Continuum 不是"另一种 LRU 变体"**：LRU（含 ARC、RLT）回答"缓存满时逐出谁"，是纯 L1 问题；Continuum 回答"请求完成后还把 KV 留多久、以及下一个请求该排在哪儿"，是 L2/L3/L4 问题。把 Continuum 称作 LRU 变体会把本项目的 Entry 层研究一起抹掉。

### 6.2 KVFlow 与 CacheWise —— 都面向 Agent 负载，但信号来源与用途不同

| 对比项 | KVFlow | CacheWise |
| --- | --- | --- |
| 面向的负载 | **多智能体工作流**（多 agent 协作，固定提示 + 动态后缀） | **coding agent 单体会话**（LLM 与工具交替的长闭环） |
| 信号来源 | **工作流结构**：Agent Step Graph + steps-to-execution（静态/半静态） | **工具调用元数据**：工具类型与参数 → TF-IDF + KMeans 簇内 `E[τ]`（在线观测 + 离线训练） |
| 信号用途 | 直接作为**驱逐优先级**（含共享前缀节点取最保守值） | 作为**逐出堆的优先级**，并周期性重估（`N_rebuild = 3`） |
| 额外机制 | 重叠 KV 预取（L5） | 前缀感知请求调度（L4） |
| 是否需要离线训练 | 否（需工作流定义） | **是**（80% trace 训练预测器） |
| 与本项目的关系 | Block Idea 1 的信号族候选（工作流距离） | Block Idea 2 的信号族候选（工具元数据） |

**结论**：二者都与"LLM-agent 工作负载 + 前缀复用"相关，但**一个是结构化工作流距离，一个是在线工具元数据统计**。它们与 Continuum 的在线 inter-request interval 统计也**不是同一思路的变体**：三者分别依赖工作流结构、工具元数据、请求间隔，来源不同、可得性不同、不能互相替代。

### 6.3 传统替换类：LRU vs. RLT vs. ARC

| 对比项 | LRU | RLT | ARC |
| --- | --- | --- | --- |
| 选择逻辑 | 按最后访问时间；前缀树中可采用 Leaf-LRU | 未标记叶子 token 中随机一个 | 双队列 + 幽灵缓存反馈，动态调 L1/L2 空间配比 |
| 解决的问题 | 简单的访问历史基线 | 减弱对到达顺序的依赖 | 应对访问模式多样、互相冲刷 |
| 理论竞争比 | 论文模型下 Leaf-LRU 最坏 **O(n)** | 同一模型下 **O(log n)**，并给出随机算法下界 | 无论述比分析 |
| 是否估计价值/代价 | 否 | 否（随机） | 部分（频率），但不估计逐出代价 |
| 对本项目的意义 | Baseline 1 的 Block 层规则 | 说明"比 LRU 好"不一定需要成本模型 → **消融的必要性** | 频率可作为候选复用信号；作图模板 |

### 6.4 vLLM RFC #37003 —— 保留指令接口

社区提案允许编排器对 token 范围标注**驱逐优先级与生存时间**（retention directives），未被标注的块继续走既有 LRU 路径。

- **定位**：工程提案而非论文，属于"自顶向下由调用方指定优先级"路线；
- **与我们的关系**：它提供由调用方声明保留优先级的接口；本项目研究由系统在线估计并排序。两者可以互补；
- **证据等级**：**不是同行评审论文，不得作为性能收益证据**。仓库参考笔记记载其标题为 "Context-Aware KV-Cache Retention API (Prioritized Evictions)" 且当时为 Open 状态；**当前状态本次未能核验**。

## 7. 四个方向与最接近工作的区分

不按"我们的方法 vs 某篇论文"组织，而按四个研究方向分别指出最接近的工作与必须守住的边界。**四个方向是潜在未来研究方向，不是已批准的实施任务，也不属于冻结的 Phase 3 评估战役。**逐方向的实现状态、CPU/Mock 与真实 vLLM 执行边界、独立评估状态见 [`../kv_cache_optimization_motivation_and_design_proposal.md`](../kv_cache_optimization_motivation_and_design_proposal.md) §3 状态矩阵；本文只做文献层面的区分，不复述完整提案。

### 7.1 Block Idea 1（介入门槛与 Native-LRU 回退）

| 最接近的工作 | 可借鉴之处 | 必须守住的边界 |
| --- | --- | --- |
| *When Fancy Eviction Fails* | 提供"复杂策略未必优于 LRU"的系统性反向证据与真实生产 trace 规模；三项设计原则 | 论文结论不能移植为本项目结论；**且必须同时引用其反例**（24 GiB Qwen To-B 上 ARC/S3-FIFO 0.491 vs LRU 0.403），不得概括为"LRU 普遍最优"；不得仅据标题推断其方法 |
| vLLM 原生 LRU / A2 已有回退路径 | 给出真实基线的候选约束与排序语义 | 离线 `native_selection()` / `native_lru_order()` 只按 `native_rank` 排序、**不含 tier 约束**，不是 A0 基线 |

### 7.2 Block Idea 2（Continuum 中间信号）

| 最接近的工作 | 可借鉴之处 | 必须守住的边界 |
| --- | --- | --- |
| Continuum | 中间信号的来源与生命周期：inter-request interval、排队延迟 T、`η`、`Prefill-Reload` | 这些信号当前只进 `estimate_ttl()`，**只有 `deadline_timestamp` 到达 Block 层** |
| CacheWise | 工具调用元数据可作为复用预测信号；调度与驱逐分别归因的实验设计 | **不得**假设其信号已被本仓库实现；本项目 `ExternalToolDurationHistory` 只写不读；**不得**把其 3.5× 端到端数字当作驱逐分量（纯驱逐仅 ~1.7×–2×） |
| KVFlow | 提供与在线信号不同来源的信号族（工作流距离） | 依赖 ASG，**不能默认在驱逐时刻可用**；不得把论文加速比当作预期收益；其预取机制不属本项目范围 |
| WFEF | compute-aware / quick demotion / capacity-adaptive granularity 三项原则 | 其成本模型与容量点均为论文自定；结论存在容量相关反例 |

### 7.3 Entry Idea 3（unpin 排序）

| 最接近的工作 | 可借鉴之处 | 必须守住的边界 |
| --- | --- | --- |
| Continuum 压力释放（冻结 A0 顺序） | 给出被冻结的基线顺序与 newly-eligible Block 计算 | **论文的释放规则是 latest program arrival（死锁预防），项目 A0 是 earliest deadline → native LRU rank，是 `baseline-freeze.md` §8 声明的适配**；A0 已消费 `native_lru_rank`，headroom 可能很小；**不得**把它说成随手实现的启发式 |
| SAGA 的显存压力缩放 TTL | 说明保留时长、内存压力与驱逐排序可分开设计 | SAGA 需要 AEG，本项目不接入 |
| A1 的 54/54 复现 | 直接的反向警示：更丰富的排序可能退化成简单规则 | 必报 pairwise ordering agreement 与 rank correlation，不能只报 outcome 差异 |
| RLT | 竞争比分析可作为理论工具 | 竞争比是最坏情况结论，不能预测平均性能 |

### 7.4 Entry Idea 4（unpin 粒度）

| 最接近的工作 | 可借鉴之处 | 必须守住的边界 |
| --- | --- | --- |
| *When Fancy Eviction Fails* §5.2 / §5.3 | compute-aware eviction 与 block-level vs session-level **驱逐**粒度的权衡 | 论文的部分粒度讨论**不等于**本项目的 partial-tail unpin——那是**驱逐**粒度，这是**保护释放**粒度，不在同一决策层 |
| KVFlow §3.1 | 树状结构中共享前缀的保留方式（共享节点取最保守优先级） | 其依赖 ASG；且共享节点保留是**驱逐优先级**问题，不是保护粒度问题 |
| vLLM RFC #37003 | token 范围保留指令的接口先例 | RFC 不是性能证据，且其状态未经核验 |

### 7.5 一个跨方向的共同约束

*When Fancy Eviction Fails* 对四个方向提出同一个要求：**复杂不等于更好**。因此每个方向都必须回答"相对简单规则的实际改进是什么"，而不是"规则之间是否存在差异"。

同时，RLT 的理论结果（随机化在其模型下也能改善 LRU）与 A1 的 54/54 复现（更丰富的排序退化为简单规则）从两个方向给出同一教训：**收益必须归因到具体信号，不能归因于复杂度。**
