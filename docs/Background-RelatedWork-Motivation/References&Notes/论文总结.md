## 1. PagedAttention / vLLM —— 背景与实验载体（L0）

> 文献：*Efficient Memory Management for Large Language Model Serving with PagedAttention*，arXiv:2309.06180v1，2023-09-12。

### 1.1 统一模板

| 字段 | 内容 |
| --- | --- |
| **研究问题** | 连续内存分配造成的内部/外部碎片与重复存储，限制了批大小与吞吐 |
| **系统上下文与负载** | 单机 GPU serving；OPT/LLaMA 系列；ShareGPT、Alpaca、翻译、并行采样、beam search |
| **主要决策层** | **L0 内存布局与块管理**。论文不定义驱逐策略本身 |
| **核心机制** | 借鉴 OS 虚拟内存把 KV 缓存切成固定大小块、非连续存放、按需增长；块表映射逻辑块到物理块；跨请求共享 + Copy-on-Write |
| **信号与元数据** | 块表、内容哈希、`ref_cnt` |
| **决策粒度** | 块（固定 block size）；驱逐是**序列级 "all-or-nothing"** |
| **信息需求** | 无外部信息 |
| **评估方法** | 与 FasterTransformer/Orca 对比吞吐；块大小消融；recomputation 与 swapping 开销分解（Figure 19） |
| **论文报告结果（条件）** | 传统系统 KV 缓存内存利用率仅 **20.4%–38.2%**（as low as 20.4%）；吞吐相对 SOTA 提升 **2–4×**；recomputation 开销**从不高于 swapping 时延的 20%** |
| **局限与范围** | "全有或全无"以序列为单位，未给出按候选块重算损失排序的策略；交换 vs 重算的结论依赖其硬件 |
| **与本项目的关系** | 运行载体（vLLM 0.27.1 + GPU APC），**不修改该机制**；使块级驱逐决策成为可能 |

### 1.2 需要继承与需要划清的设定

- **需要继承**：块级（固定大小块）的缓存管理粒度。A0 的 Block 层基线是"现有 eligibility 下的 native LRU"，采用 vLLM 原生前缀缓存的逐出语义（vLLM v0.6.0 文档记载：只考虑 `ref_cnt = 0` 的块，多候选时优先最久未使用，时间相同则优先最长前缀末端；见 [`参考文献/关于vLLM的参考文档与网址.md`](参考文献/关于vLLM的参考文档与网址.md)），**不**将其表述为 PagedAttention 论文的默认逐出实现。
- **需要划清**：仓库内 `参考文献/paged_attention.md` 是 vLLM 官方对 **attention kernel 实现**的说明，文首自带 "historical document ... no longer describes the code used in vLLM today" 警告。它**不是论文、不含驱逐策略语义**，不得作为逐出行为依据。

### 1.3 对本项目的启发

- **正面**：分页使"以块为单位做驱逐决策"成为可能，Block 层研究天然作用在块/前缀粒度上。
- **启发**：交换 vs 重计算的权衡分析，可作为定义"重算成本"信号时的依据（但注意本项目不做 offload，只借用其代价排序）。
- **局限**：论文讨论的"全有或全无"恢复方式以序列为单位，未给出按候选块重算损失排序的策略。项目若改为块级排序，需要在实现中确认不破坏后端的块表和引用计数约束。

## 2. Recency/Frequency Adaptive KV Caching（ARC）—— 自适应但仍"成本盲目"（L1）

> 文献：*Recency/Frequency Adaptive KV Caching for Large Language Model Serving*，arXiv:2606.21238v1，2026-06-19。

### 2.1 统一模板

| 字段 | 内容 |
| --- | --- |
| **研究问题** | LRU 只看新近度，无法应对多样化负载；不相关的工作负载会互相冲刷缓存 |
| **系统上下文与负载** | vLLM 内实现；**Qwen3-14B**、单张 **H100 PCIe 80GB**；KV block size 固定 **16 token**；QuALITY、WikiQA 两个文档 QA 负载 + Zipf（指数 1.0）合成负载 + 真实多轮对话 trace |
| **主要决策层** | L1 驱逐 + **两类队列的空间配比** |
| **核心机制** | 双队列（低频 L1 / 高频 L2，L1 中被再次命中的项晋升 L2）+ **Ghost Cache**（只记录被逐出块的元数据，估计"如果缓存更大能否命中"）作为反馈信号，动态调整 L1/L2 物理空间配比 |
| **信号与元数据** | 新近度、频率、幽灵缓存命中反馈 |
| **决策粒度** | 块 / 队列 |
| **信息需求** | 无外部工作流信息 |
| **评估方法** | 命中率 + TTFT vs 缓存大小；跨 batch size；观察两类队列尺寸随时间变化以论证自适应必要性；隔离双队列与自适应配比各自的贡献 |
| **论文报告结果（条件）** | 相对朴素 vLLM：合成文档 QA 上命中率最高 **+10.8%**、TTFT 最高 **−12.6%**（§4 细分 QuALITY **+1.2%–10.8%**、WikiQA **+2.5%–7.8%**）；真实多轮对话负载上 **+2.1% / −2.0%** |
| **局限与范围** | 信号仍只回答"会不会再被访问"，不回答"被逐出后再访问要多大重算代价"；块大小固定；对显存压力与排队无反馈 |
| **与本项目的关系** | **机制对照，不复现为基线**。说明"自适应"仍不等于"感知逐出代价" |

### 2.2 基线复现价值

**不复现为基线**。它的价值是 Related Work 中的"中间档位"：相对 LRU 增加了频率维度与自适应空间配比，但其信号仍不回答逐出代价。其实验设置可作为参考：对比纯 LRU，使用 QuALITY、WikiQA、合成 Zipf 负载和多轮对话 trace，并报告命中率与 TTFT。最终数据集和指标仍以 `docs/experiment-plan.md` 为准。

### 2.3 对本项目的启发

- **可借鉴**：
  - 频率是一个独立于新近度的有效复用信号，Block Idea 2 可把"近期复用历史"纳入候选信号；
  - 评估函数不应是静态的，应随负载动态调整——呼应"在线动态感知"的定位；
  - 幽灵缓存提示：即使一个块当前不活跃，也可以低成本地保留它的元数据来估计潜在收益。
- **局限（即本项目要检验的空白）**：
  - **不感知逐出代价**：ARC 只关心"会不会再被访问"，不关心"被逐出后再访问要花多大代价"；
  - **不感知异构代价**：不同长度、不同位置的块被一视同仁；
  - **自适应范围有限**：它调的是新近度/频率的配比，而不是对实时系统状态（显存压力、排队）的响应；
  - 实验中 KV 块固定为 16 token，未考虑不同内存足迹下的价值最大化。

## 3. Randomization-Boosts-KV-Caching（RLT + LBGR）：理论参照（L1 + L4）

> 文献：*Randomization Boosts KV Caching, Learning Balances Query Load: A Joint Perspective*，ICLR 2026，arXiv:2601.18999v1，2026-01-26。

### 3.1 统一模板

| 字段 | 内容 |
| --- | --- |
| **研究问题** | LRU 对动态在线查询到达顺序脆弱；多 LLM 场景下缓存亲和与全局负载均衡目标冲突 |
| **系统上下文与负载** | SGLang 默认的 **L-LRU（Leaf-LRU）** 为驱逐基线；Llama-3.1 8B/70B 与 Mixtral 8×7B（8B 用 10×L40，70B 与 Mixtral 用 4×H200）；1–10 worker（默认 4）；三类前缀共享负载——GSP 合成基准、ShareGPT/UltraChat 多轮对话、Loogle 长文档 QA；输出 4–128 token；random 与 worst-case round-robin 两种到达顺序 |
| **主要决策层** | L1 驱逐（RLT）+ L4 请求路由（LBGR） |
| **核心机制** | **RLT**：缓存满时从**未标记的叶子 token 中随机选一个逐出**，用随机化打破对到达顺序的依赖；**LBGR**：用在线学习估计端到端延迟（服务时间 + 队列负载 + 残差校正）来路由请求 |
| **信号与元数据** | 随机性（RLT）；端到端延迟的在线估计（LBGR） |
| **决策粒度** | 叶子 token（RLT）；查询 / worker（LBGR） |
| **信息需求** | 论文模型下的前缀共享结构与到达顺序假设；无需先验工作流信息 |
| **评估方法** | 理论竞争比分析（Theorem 4/5/8、Corollary 9，含随机算法下界）+ 跨 benchmark 实验；命中率、P50/P95 时延与 TTFT、吞吐；驱逐与路由的运行时开销分解 |
| **论文报告结果（条件）** | 理论：Leaf-LRU（L-LRU）最坏竞争比 **O(n)**，RLT 改善到 **O(log n)**；实验：相对 SOTA（Cache-Aware+LRU 等）命中率最高 **6.92×**、时延最高降低 **11.96×**、TTFT 最高降低 **14.06×**、吞吐最高提升 **77.4%** |
| **局限与范围** | RLT 逐出决策**完全随机**，不评估单个块的价值或逐出代价；成本估计只发生在**路由**侧（对整个查询），不在**驱逐**侧（对单个块）；未利用共享度、访问频率与内存足迹 |
| **与本项目的关系** | **理论参照，不复现**。证明"比 LRU 好"不一定需要成本模型，因此本项目必须用消融证明收益来自成本信号本身 |

> **论文内部不一致**：摘要称 "4 benchmarks and 3 prefix-sharing settings"，§5 只列 3 类负载（GSP、ShareGPT/UltraChat、Loogle）。引用时按 §5 明细更稳。

### 3.2 对 LRU 的批判（可直接引用为动机素材）

- 对动态在线查询脆弱，容易逐出后续就要用的 KV，导致未命中与延迟上升；
- 多 LLM 场景下，缓存亲和与全局负载均衡目标冲突，LRU 表现不稳；
- **理论上**：前缀共享结构下 LRU 最坏情况竞争比退化为 \(O(n)\)。

### 3.3 基线复现价值

**不复现为基线**（超出项目范围）。它说明在论文给定的前缀共享和到达顺序条件下，随机化也能改善 LRU；实验讨论中应说明本项目与其比较的是**决策信号**，而非直接比较性能。**指标体系直接复用**：命中率、吞吐、延迟与 TTFT（P50/P95），以及驱逐与路由的**运行时开销分解**——这正是本项目实验计划中"优化开销"一节的范本。

### 3.4 对本项目的启发

- **可借鉴**：
  - "在随机/简单选择之前先排除高价值项"的思路，可与成本排序互补；
  - LBGR 的延迟估计公式（服务时间 + 队列负载 + 残差校正）提示：驱逐侧的估计也可以是**多维信号的在线估计**，而非固定公式；
  - 竞争比分析为评价本项目策略提供了理论工具（至少可以引用）。
- **局限（即本项目要检验的空白）**：
  - RLT 的逐出决策是**随机的**，完全不评估单个块的"价值"或"逐出代价"；
  - 成本估计只发生在**路由**环节（对整个查询），而不是**驱逐**环节（对单个块）；
  - 未利用共享度、访问频率等更细的复用信号；内存足迹也不在决策内；
  - 其成本模型聚焦时间维度，没有刻画异构的逐出代价（如长前缀重算对 TTFT 的破坏）。

## 4. Continuum —— A0/A1 的来源与基线（L2 + L3 + L4）

> 文献：*Continuum: Efficient and Robust Multi-Turn LLM Agent Scheduling with KV Cache Time-to-Live*，arXiv:2511.02230v6，2026-05-25。

### 4.1 统一模板

| 字段 | 内容 |
| --- | --- |
| **研究问题** | Agent 工具调用期间 LLM 暂停，**end-of-turn eviction** 会丢弃随后就要用的 KV 缓存，并造成逐出后的排队延迟（"调度气泡"） |

### 4.2 信号与元数据（逐项，含冷启动）

- **`P(τ,f)`**：经验 CDF，样本是**服务端 inter-request interval** `t_arrive(i+1) − t_finish(i)`。论文 §5.1 原文明确："We record this interval as the execution time of the tool call this time to store for TTL computation in the future." **因此本项目用 `server_inter_request_gap` 作为 TTL 分布样本是对论文的忠实继承，不是项目自创的偏离**——这一点此前的文档没有写清，容易被误读为项目适配。
- **`T`**：被逐出请求经历的 queueing delay 的**滑动窗口平均**（论文术语是 "queueing delay"）。
- **`η = −Corr(k, N−k)`**：memoryfulness factor，`k` 为已服务请求数、`N` 为程序总请求数。完全 memoryless 时 `η=0`，程序请求数固定时 `η=1`，极端长尾轮次分布下**可能为负**（anti-memoryful）。论文称未观测到负值但机制上支持。
- **`Prefill-Reload(r)`**：由**离线剖析**得到——按 chunk size `{1000, 2000, 4000, ...}` 测 prefill 并拟合二次曲线；另测 CPU offload 带宽。每个 hardware-model pair 剖析 < 10 分钟。
- **冷启动层次**（论文 §4.2）：`|S| ≤ K`（实现中 **K=100**）时用固定 `T_default`（假设 `ToolCallDuration ~ Exp(1)` 且 `η=1` 下的最优 τ）；否则 `|S[f]| ≤ K` 时用全局记录；否则用细粒度按工具类型估计。

### 4.3 核心算法（复现指南）

1. **`CalcTTL`**：求解式 (2)
   $$\tau^* = \arg\max_{\tau}\; P(\tau, f)\times\bigl(T\cdot\eta + \mathrm{Prefill\text{-}Reload}(r)\bigr) - \tau$$
   候选集为 `S[f]` 中全部已观测时长**加上 τ=0**，暴力枚举取期望奖励最大者。
2. **软保护 / 解除保护**：请求含工具调用且非最后一步时 `pin_request(request, τ*)`；`unpin_requests()` 在每个调度步开始时解除"TTL 已过期**且**该 `program_id` 不在等待队列"的条目；程序最后一步完成时主动解除该 program 的全部 pin。
3. **死锁预防**：调度因空间争用失败时，按 **latest program arrival time** 迭代从 `pinned_requests` 选 victim 解除保护并释放空间，直到第一个请求可被调度。
4. **调度优先级**（多键元组，按序比较）：preempted 状态 > TTL 窗口内 > program-level arrival order。
5. **核心数据结构**：`pinned_requests`（request → expiration timestamp）；按工具类型（及全局）保留完整时长样本集合 `S[f]` / `S`。

### 4.4 基线复现价值（A0/A1 的来源）与两处必须声明的项目适配

复现范围聚焦其**决策逻辑**，而非整套系统。**边界提醒**（与 `docs/baseline-freeze.md` 一致）：项目实现的是**适配到 vLLM 0.27.1 的 Continuum 风格基线**，因为 vLLM 缺少 Continuum 原生的程序/会话身份、pin API、工具间隔状态与程序级调度原语。该基线**不得被描述为源码级的精确复现**，也不得退化成普通 LRU。

两处项目适配必须显式声明，不得说成论文规则：

1. **压力释放顺序**。论文的释放规则是 §5.2 的**死锁预防**：按 *latest program arrival time* 迭代解除保护。项目 A0 冻结的是
   ```text
   earliest retention deadline first
       -> native LRU rank as tie-breaker
   ```
   `docs/baseline-freeze.md` §8 明确其为 "an adaptation, not a claimed native Continuum rule"。代码中对应 `_release_sort_key()`（`src/kvopt/continuum/pressure.py`），返回 `(entry.deadline_timestamp, native_key, key.sort_key)`，其中 `native_key` 是该 Entry 释放后**新获得资格的 Block** 中最小的 `native_lru_rank`。代码注释称其为**冻结的 A0 顺序**，不得描述为随手实现的启发式。
2. **无原生 pin API**。冻结适配是"项目独立保护表 + 驱逐候选过滤"：受保护块仍留在原生 free queue 中并保留 APC 哈希元数据，**禁止**用抬高 `ref_cnt`、移入隐藏池或复制 BlockPool 记账来模拟 pin（`docs/baseline-freeze.md` §6）。

TTL 语义（CDF 构造、候选枚举、冷启动层次等）以 `docs/archive/phase1b-continuum/phase1b-continuum-implementation-decisions.md` §1 为准。

### 4.5 对本项目的启发

- **可借鉴**：
  - "保留决策需要量化收益"的思想：保留的收益 = 省下的重算 + 省下的排队，代价 = 占用的显存时间；
  - 在线收集请求间隔统计并更新预测——一种轻量的"在线感知"范式；
  - 其局限即为本项目的研究空间（见下）。
- **与本项目的两层决策的关系**：
  1. Continuum 会在调度失败时解除部分保护以避免死锁，但其主要输出仍是每个程序/会话的 TTL，而非对全部可逐出块的统一排序；
  2. TTL 依赖 inter-request interval 历史。冷启动、间隔分布变化或长尾都会影响估计质量；
  3. 论文的保留和解除保护以请求的 KV 缓存为单位，不区分同一请求内不同块的重算价值；
  4. **本项目在 Entry 层研究释放顺序与释放粒度，在 Block 层研究受害者选择**；这两个决策点可与 TTL 保留组合，但是独立可检验的研究问题（Entry Idea 3 / Idea 4，Block Idea 1 / Idea 2）。

### 5.3 核心机制细节

- **工具调用感知 TTL**（§4.2）：
  - 基础 TTL 取特定工具类型预期时延的 **p 分位数**，`p` 可配置，**默认 95%**（用指数移动平均更新）；
  - **显存压力大时按比例缩短 TTL**；设最大上限 **`TTL_max = 300s`**；
  - 过订阅（利用率 >95%）时优雅退化为标准 LRU（Eq. 6）；
  - 内存压力达到高阈值时触发硬驱逐，TTL 不是无限期保护。
- **WA-LRU**（§4.1）：三个**归一化**因子——AEG 预测的未来复用概率、新近度、缓存大小——构成逐出排序分。
- **AEG 来源**（§3.2 / §3.3）：编排框架 hint（LangChain callbacks、AutoGen message logs）或 §3.3 的 pattern inference。
- **KV 缓存规模**：论文 §2.2 给出 "For Llama-3-70B with GQA (L=80, n_kv=8, d_h=128) and 32K context in FP16, each session requires ~10.7 GB"，另述 "2 to 12 GB per session"。**引用 2–12 GB 时必须附带该条件。**

### 5.4 基线复现价值

**不复现为基线**。其价值有两点：

1. 作为 A0 / Baseline 2 的对照设计参考，帮助说明**保留时长、内存压力和驱逐排序可以分开设计**；
2. WA-LRU 是信号设计上最接近 Block Idea 2 的相关工作之一。两者的主要区别是 SAGA 使用 AEG 预测复用，而本项目**拟检验**是否能在不接入 AEG 的条件下，仅用本地运行时历史估计复用并改进受害者选择。**这是待检验假设，不是已成立的区别。**

### 6.2 核心机制

- **Agent Step Graph（ASG）与 steps-to-execution**（§3 引言、Figure 3(a)）：把 agent 执行计划抽象为图，每个 agent 赋予一个 `steps-to-execution` 值，估计它距未来被激活还有多少步。用 step aggregation 函数（`Max(E1,E2)+1` / `Min(E1,E2)+1`）在依赖边上计算，表达同步屏障与 AND/OR 条件分支。
- **工作流感知的驱逐优先级传播**（§3.1，Figure 3(b)）：按 steps-to-execution 在缓存树上传播驱逐优先级；**steps-to-execution 越小保留越久**；聚合多 agent 输入的节点取其子节点中**最低（最保守）**的优先级，保证**共享节点只要对任一 agent 在不久的将来有用就被保留**；并发工作流在共享节点上的冲突以最低（最保守）优先级解决。论文摘要明确称其在树状结构中高效管理**共享前缀**。
- **重叠 KV 预取与状态感知调度**（§3.2）：后台线程把下一步调度到的 agent 所需张量从 CPU 预取到 GPU。**预取与本项目研究的驱逐是不同问题。**

### 6.3 与本项目的启发与限制

- **对 Block Idea 1**：提供了一个"何时值得偏离 LRU"的信号族候选——工作流/未来执行距离。但**它依赖工作流执行信息**；本项目在真实驱逐时刻能否获得这类信息必须单独验证，不能默认可用。
- **对 Block Idea 2**：KVFlow 的信号是**结构化、静态/半静态的工作流距离**；Continuum 的信号是**在线观察量**（请求间隔、排队延迟、工具统计）。二者来源不同，不能互相替代，也不必然相关；应作为独立的信号族对照，而非同一思路的变体。
- **限制**：不得把 KVFlow 的论文结果当作本项目的预期收益；不得把其预取机制与本项目的驱逐研究混为一谈。

### 7.2 核心机制（论文分三部分，不应笼统概括为"使用工具元数据"）

- **§3 Coding Agent Workloads（负载特征）**：分析 coding agent 的会话结构、上下文长度增长、轮次类型分布。其中报告**工具元数据（如工具类型与参数）能捕捉执行行为的有意义结构**。

- **§5 CACHEWISE Design（方法）**：
  - **§5.1 Prefix-aware Request Scheduling**：按请求与 XPU 常驻 KV 的重叠度排序，提高复用；
  - **§5.2 Predictive KVCache Eviction**：块级管理器为每个 KVCache 块附加会话级元数据 `tool_name` / `tool_args` / `T_i`；请求完成且 `ref_cnt` 归零后块进**逐出堆**，轻量预测器据 `S_i` 估 `E[τ_i(t)]` 作为优先级；对工具参数做 **TF-IDF 嵌入 + KMeans 聚类**，用簇内分布代替按工具分布（因为同名工具（如 bash）的执行时间高度依赖参数与环境）；因预测随时间过期，按 `N_rebuild`（实验取 **3**，单位为 engine iteration）周期性重估并重建堆；

| **主要决策层** | **L1 驱逐算法本身**（跨 HBM 与内存池两种机制） |
| **核心机制** | 评估 **14 种在线驱逐算法**并以 Bélády 离线最优为 ceiling（见 §8.1 的分组名单）；提出三项设计原则：quick demotion（§5.1）、compute-aware eviction（§5.2，含 partial-node 驱逐）、capacity-adaptive eviction granularity（§5.3 Block-Level vs Session-Level） |
| **信号与元数据** | recency、frequency，以及上述三项原则；**无需先验工作流信息** |
| **决策粒度** | 块 / 会话级（§5.3 对照）/ partial-node（§5.2） |
| **信息需求** | 无外部工作流信息 |
| **评估方法** | 容量受限 per-replica HBM（**24–120 GiB/GPU**：Table 2 给出 24 GiB = 16,384 块（native-context floor）、48 GiB = 32,768 块（1×H200 @0.8 memory fraction）、96 GiB = 65,536 块（1×B200 bf16））与全局内存池（**0.25–12 TiB**：1 TiB = 699,051 块 = Mooncake 整节点）；块命中率、compute-savings ratio、与 BeladyCompute 离线上界的距离；TTFT 与 prefill 吞吐；附录 A 做 65 个容量的密集扫描，附录 B 做并发度敏感性，附录 C 用理想线性成本模型，附录 D 报告重算碎片化 |
| **论文报告结果（条件）** | 见 §8.3 |
| **局限与范围** | 容量点、硬件、模型与 trace 均为论文自定，**不可直接照搬**；命中率类结果主要来自自建模拟器与 trace 回放，只有 Figure 7/8/13 报告真实 GPU/vLLM 测量 |
| **与本项目的关系** | **四个方向共同的反向证据来源** |

**评估的 14 种在线算法**（§3.2 按设计原则分组）：recency 的 **LRU**（baseline）；quick demotion 的 **ARC / Sieve / S3-FIFO / S4-FIFO / LIRS**；analytic modeling 的 **LHD**；frequency 的 **LFU / W-TinyLFU**；learned 的 **LeCaR / LRB / 3LCache**；domain-specific 的 **Workload-aware / AsymCache**。**Belady's optimum 是离线 ceiling，不属于 14 种在线算法**；附录 A 的 65 容量密集扫描因 LRB 过慢而排除它。

### 8.2 结构性解释（论文 §4）

- **§4.1 Session-Bounded Lifetimes / §4.2 Recency Provides a Key Signal**：前缀复用主要由**活跃会话的稳定节奏**主导，使 recency 成为异常强的预测因子；
- **§4.3 Frequency Tracks Session Progress**：频率类信号的效果与会话进度耦合；
- **§4.4 Position-Dependent Miss Costs**：miss cost 因注意力计算随 token 深度增长而**高度非均匀**；
- **§4.5 Heavy-Tailed Session Footprints**：会话足迹极度倾斜（Figure 10a：中位每会话仅 **45 块**，重尾）；
- **§4.6 Findings Generalize Across Workloads**：结论跨负载的泛化范围；
- **前缀缓存与传统负载的差异**：单轮请求普遍、会话足迹极度倾斜、非均匀 miss cost。论文 Table 4/5 用 Wikipedia（CDN，207.6M 请求 / 18.4M 对象 / 21.0 天）与 CloudPhysics w01（磁盘 I/O，215.8M 请求 / 122.8M 对象 / 6.3 天）作对照，论证"Web 缓存结论不可直接迁移到前缀缓存"。

### 8.3 原文结论（论文报告，非本项目结果）

- 简单 LRU **出乎意料地稳健**，与复杂的传统策略表现相当（**频率类算法往往更差**）；同时距 Bélády 最优仍有可观的剩余空间；
- **设计原则**（论文原话）："keeping recency as the baseline while incorporating quick demotion to filter one-hit prompts, compute-aware eviction to prioritize expensive misses, and capacity-adaptive eviction granularity"；
- **反例（引用时必须同时给出容量与 trace）**：Figure 11 在 **24 GiB** 的 Qwen To-B 上 S3-FIFO 与 ARC 达 **0.491**、LRU 为 **0.403**——说明"LRU 稳健"依赖容量与负载，**不得概括为"LRU 普遍最优"**；
- **附录 A 的非单调性**：quick demotion 的收益随容量增长可能**反转**（Qwen To-C 上 LIRS 从高于 LRU 4.2 点变为低于 10.1 点 @724GB，之后又收敛）；W-TinyLFU 对缓存大小**非单调**（FreeInference 上命中率 0.866@97GB → 0.759@906GB → 0.933@12TB）；
- **附录 B 的并发度效应**：FreeInference Trace 平均约 12 个并发会话；除 W-TinyLFU 外所有策略在容量扫描中与 LRU 相差约 1 点以内；固定 48 GiB HBM + 1 TiB pool 后合成变化并发度（每点重放同样 73,637 个请求），**所有策略的命中率都随并发度上升而下降**。

### 11.2 支撑实验方案设计

- **指标体系**：命中率、TTFT（P50/P95）、吞吐、端到端延迟/完成时间；另记录驱逐次数、重算量与策略决策开销。证据分层按 `N`/`E`/`C`/`R`/`W`/`S` 报告（见 [`../专业术语表.md`](../专业术语表.md) §7）。
- **必报的诊断量**：候选方法间的 pairwise ordering agreement 与 rank correlation（Entry Idea 3），以及强制首释放窗口计数。
- **作图模板**：命中率 / TTFT vs. 缓存大小（ARC 图 3–5）；不同负载压力下的对比（ARC 图 6）；多容量点扫描（WFEF 附录 A 的非单调性教训）。

### 11.3 明确不做的事（范围控制）

- 不复现 PagedAttention / vLLM 本身，不改注意力内核，不做多卡与分布式，不做 CPU KV offloading；
- 不复现 ARC、RLT/LBGR、SAGA、KVFlow、CacheWise 的完整系统；
- Continuum 风格基线复现其动态 TTL / retention 与程序级调度决策逻辑，不复现其完整系统，也不声称与论文逐行等价（[`../../baseline-freeze.md`](../../baseline-freeze.md)：只做 retention 不足以构成该基线）；
- 四个优化方向的评分函数、信号权重、介入阈值与 partial-tail 规则**尚未冻结**，一律保持 proposal / hypothesis 定位。
