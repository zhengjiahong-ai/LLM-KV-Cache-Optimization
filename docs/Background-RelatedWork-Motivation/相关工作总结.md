## 1. 决策层分类：先分清各工作改的是哪一层

相关工作的差异首先在**决策层**，而非策略复杂度。同一层内才可比较性能，跨层比较必须先说明比较的是什么。

| 决策层 | 决策内容 | 典型工作 |
| --- | --- | --- |
| L0 内存布局 | 块表、分页、写时复制、`ref_cnt` | PagedAttention / vLLM |
| L1 驱逐 / victim selection | 在可驱逐候选中最终移除哪些物理块 | ARC、RLT、SAGA(WA-LRU)、KVFlow、CacheWise、WFEF、vLLM 原生 LRU |
| L2 保留时长 / TTL | 受保护条目保留多久后失效 | Continuum、SAGA |
| L3 保护与释放 / unpin | 压力下释放哪些条目的保护，使其 Block 获得被回收**资格** | Continuum（论文为 latest-arrival 死锁预防）、**本项目 A0/A1** |
| L4 准入与调度 | 请求/程序的执行顺序 | Continuum（program-level FCFS + TTL 优先级）、SAGA（workflow-atomic + session-affinity batching）、CacheWise（prefix-aware scheduling） |
| L5 预取 / offload | 把 KV 从 CPU 搬到 GPU，或换出到 CPU | KVFlow（overlapped prefetch）、PagedAttention（swap vs recompute） |
| L6 工作流级协调 | 集群级路由、工作窃取、公平性 | SAGA（session-affinity batching + work stealing + AFS） |

本项目关注的两个决策层是 **L3（Entry 级 unpin / pressure release）** 与 **L1（Block 级 physical eviction）**，二者在代码中也是两条独立路径：

| 层级 | 决策内容 | 本项目代码位置 |
| --- | --- | --- |
| Entry 级 unpin / pressure release | 压力下释放哪些 Entry 的保护，使其关联 Block 获得被回收**资格** | `src/kvopt/continuum/pressure.py` |
| Block 级 physical eviction | 在可驱逐候选中最终移除哪些物理块 | `src/kvopt/runtime/vllm/adapter.py`、`src/kvopt/costaware/a2_native.py` |

> **一句话口诀**：unpin 改**资格**，victim selection 选**对象**，eviction 才**移除**。三者不可互换，也不互相蕴含（详见 [`专业术语表.md`](专业术语表.md) §1）。一篇论文可以只动一层，也可以多层叠加；比较时必须对齐层级。

## 2. 逐篇梳理（按五个主题类组织）

> 每篇的完整版本号、作者与链接以 [`文献索引.md`](References&Notes/参考文献/文献索引.md) 为准。以下"论文报告结果"一栏中的数字**全部属于原论文的实验条件，不是本项目实测，也不构成本项目预期**。

### 2.A 类一：KV-cache 基础设施与前缀缓存（运行载体，不是被比较的策略）

#### 2.A.1 PagedAttention / vLLM —— L0

- **研究问题**：连续内存分配造成的内部/外部碎片与重复存储，限制了批大小与吞吐。
- **系统上下文与负载**：单机 GPU serving；论文用 OPT/LLaMA 系列，负载含 ShareGPT、Alpaca 与翻译/并行采样/beam search 场景。
- **主要决策层**：L0 内存布局与块管理。论文**不定义**驱逐策略本身。
- **核心机制**：借鉴 OS 虚拟内存把 KV 缓存切成固定大小块、非连续存放、按需增长；块表映射逻辑块到物理块；支持跨请求共享与 Copy-on-Write。
- **信号与元数据**：块表、内容哈希、`ref_cnt`。
- **决策粒度**：块（固定 block size）；论文的驱逐是**序列级 "all-or-nothing"**——要么整个序列的块一起被驱逐。
- **信息需求**：无外部信息。
- **评估方法**：与 FasterTransformer/Orca 对比吞吐；消融块大小；测量 recomputation 与 swapping 的开销分解（Figure 19）。
- **论文报告结果（附条件）**：传统系统 KV 缓存内存利用率仅 **20.4%–38.2%**（as low as 20.4%）；吞吐相对 SOTA 提升 **2–4×**；recomputation 开销**从不高于 swapping 时延的 20%**，块小时重算更优、块大时交换更优。
- **局限与范围**：论文的"全有或全无"以**序列**为单位，未给出按候选块重算损失排序的策略；交换 vs 重算的权衡分析依赖其硬件配置。
- **与本项目的关系**：本项目跑在 vLLM 0.27.1 + GPU APC 上，**不修改该机制**。它使"以块为单位做驱逐决策"成为可能。vLLM v0.6.0 文档记载的前缀缓存逐出语义（只考虑 `ref_cnt = 0` 的块；多候选时优先最久未使用；时间相同则优先最长前缀末端）可作为"vLLM 风格 LRU"的语义参考，但**不等同于当前所有版本的默认行为**（见 [`关于vLLM的参考文档与网址.md`](References&Notes/参考文献/关于vLLM的参考文档与网址.md)）。**不得**把该语义说成 PagedAttention 论文的默认逐出实现。

### 2.B 类二：传统缓存替换方法（单机、在线、无外部信息）

#### 2.B.1 ARC —— L1 + 空间配比

- **研究问题**：LRU 只看新近度，不相关负载互相冲刷缓存。
- **系统上下文与负载**：vLLM 内实现；Qwen3-14B、单张 H100 PCIe 80GB；KV block size 固定 **16 token**；QuALITY、WikiQA 两个文档 QA 负载 + Zipf（指数 1.0）合成负载 + 真实多轮对话 trace。
- **主要决策层**：L1 驱逐 + **两类队列的空间配比**。
- **核心机制**：双队列（低频 L1 / 高频 L2）+ **Ghost Cache**（只存被逐出块的元数据）反馈，动态调整 L1/L2 物理空间配比。
- **信号与元数据**：新近度、频率、幽灵缓存命中反馈。
- **决策粒度**：块 / 队列。
- **信息需求**：无外部工作流信息。
- **评估方法**：命中率 + TTFT vs 缓存大小；跨 batch size；观察两类队列尺寸随时间的变化以论证自适应的必要性。
- **论文报告结果（附条件）**：相对朴素 vLLM，合成文档 QA 上命中率最高 **+10.8%**、TTFT 最高 **−12.6%**（§4 细分为 QuALITY +1.2%–10.8%、WikiQA +2.5%–7.8%）；真实多轮对话负载上 **+2.1% / −2.0%**。
- **局限与范围**：信号仍只回答"会不会再被访问"，不回答"被逐出后再访问要多大重算代价"；块大小固定，未考虑不同内存足迹下的价值最大化；"自适应"只针对访问模式，对显存压力与排队无反馈。
- **与本项目的关系**：作为**机制对照**，不复现为基线。它说明"自适应"仍不等于"感知逐出代价"。其"命中率/TTFT vs 缓存大小"的作图方式是本项目实验图的直接模板。

#### 2.B.2 RLT + LBGR —— L1 + L4（成本估计发生在路由侧）

- **研究问题**：LRU 对动态在线查询到达顺序脆弱；多 LLM 场景下缓存亲和与负载均衡目标冲突。
- **系统上下文与负载**：SGLang 默认的 **L-LRU（Leaf-LRU）** 为驱逐基线；Llama-3.1 8B/70B 与 Mixtral 8×7B（Llama-3.1-8B 用 10×L40，70B 与 Mixtral 用 4×H200）；1–10 worker（默认 4）；三类前缀共享负载——GSP 合成基准、ShareGPT/UltraChat 多轮对话、Loogle 长文档 QA；输出 4–128 token；random 与 worst-case round-robin 两种到达顺序。
- **主要决策层**：L1 驱逐（RLT）+ L4 请求路由（LBGR）。
- **核心机制**：**RLT** 在未标记的叶子 token 中随机选一个逐出，用随机化打破对到达顺序的依赖；**LBGR** 用在线学习估计端到端延迟来路由请求。
- **信号与元数据**：随机性（RLT）；服务时间 + 队列负载 + 残差校正的在线延迟估计（LBGR）。
- **决策粒度**：叶子 token（RLT）；查询/worker（LBGR）。
- **信息需求**：论文模型下的前缀共享结构与到达顺序假设；无需先验工作流信息。
- **评估方法**：理论竞争比分析（Theorem 4/5/8、Corollary 9）+ 跨 benchmark 实验；命中率、P50/P95 时延与 TTFT、吞吐；给出驱逐与路由的运行时开销分解。
- **论文报告结果（附条件）**：理论上游离-LRU（L-LRU）最坏竞争比 **O(n)**，RLT 改善到 **O(log n)**，并给出随机算法的下界；实验上相对 SOTA（Cache-Aware+LRU 等）命中率最高 **6.92×**、时延最高降低 **11.96×**、TTFT 最高降低 **14.06×**、吞吐最高提升 **77.4%**。（注：摘要称 "4 benchmarks and 3 prefix-sharing settings"，§5 只列 3 类负载，论文内部数量表述不一致。）
- **局限与范围**：RLT 的逐出决策**完全随机**，不评估单个块的价值或逐出代价；成本估计只发生在**路由**侧（对整个查询），不在**驱逐**侧（对单个块）；未利用共享度、访问频率与内存足迹。
- **与本项目的关系**：作为**理论参照**，不复现。它证明"比 LRU 好"不一定需要成本模型——因此本项目必须用消融证明收益来自成本信号本身。其 P50/P95 指标报告方式与运行时开销分解直接进本项目的指标定义。

### 2.C 类三：Agent 工作流的保留与调度系统（Continuum、SAGA）

> 这一类是**系统级**工作：它们改变的是 L2/L3/L4，不是单纯的 L1 替换策略。把它们称作"另一种 LRU 变体"是分类错误。

#### 2.C.1 Continuum —— L2 + L3 + L4（本项目的 A0/A1 来源）

- **研究问题**：Agent 工具调用期间 LLM 暂停，**end-of-turn eviction** 会丢弃随后就要用的 KV 缓存，并造成逐出后的排队延迟（"调度气泡"）。
- **系统上下文与负载**：单机/少卡 vLLM 扩展（论文实现约 1k 行 Python）；Llama-3.1-8B/70B、Gemma-3-12B（摘要另含 GLM-4.5 355B）；A100-SXM（Runpod）、H100（AWS/Tensormesh）、B200（on-prem）；SWE-Bench（mini-swe-agent）、BFCL V4 Web Search、OpenHand（multi-SWE-bench Go）；**Poisson 到达**，请求由 GPT-5 生成的 agent 工作流驱动；真实 SWE-agent 500 任务分布式实验在 Tensormesh H100 testbed。
- **主要决策层**：**L2 保留时长（TTL）为主，L3 保护/解除保护与 L4 程序级调度为辅**。论文**不定义**块级 victim selection。
- **核心机制**：
  - `CalcTTL`：基于历史记录构建**经验 CDF**，在候选集 `{0} ∪ 已观测时长` 上枚举，求解式 (2) 的目标
    `argmax_τ P(τ,f) × (T·η + Prefill-Reload(r)) − τ`；
  - **软保护 + TTL 到期自动解除**；程序结束时主动解除该 program 的全部 pin；
  - **死锁预防**：调度因空间争用失败时，按 **latest program arrival time** 迭代从 `pinned_requests` 中选 victim 解除保护并释放空间；
  - **调度优先级**（多键元组，按序）：preempted 状态 > TTL 窗口内 > program-level arrival order（FCFS）。
- **信号与元数据**：
  - `P(τ,f)`：经验 CDF，样本是**服务端 inter-request interval** `t_arrive(i+1) − t_finish(i)`（论文明确"record this interval as the execution time of the tool call"）；
  - `T`：被逐出请求经历的 queueing delay 的滑动窗口平均；
  - `η = −Corr(k, N−k)`（memoryfulness factor，允许为负）；
  - `Prefill-Reload(r)`：离线剖析得到的 prefill vs 上下文长度二次曲线；
  - 冷启动：`|S| ≤ K`（K=100）用固定 `T_default`（假设 `ToolCallDuration ~ Exp(1)`、`η=1`）；`|S[f]| ≤ K` 用全局记录；否则用细粒度估计。
- **决策粒度**：**请求/程序的前缀条目**（以 `program_id` 为键），不是单个物理块。
- **信息需求**：`program_id` 由客户端附加；工具调用解析与间隔统计由 Tool-Call Handler 在线收集。vLLM 不原生提供这些原语。
- **评估方法**：trace 重放 + 真实 agent 实验；基线为 vanilla vLLM **0.10.2**、vLLM 0.10.2 + LMCache 0.3.7 的 CPU offload、Autellix(PLAS)、InferCept、SGLang 0.5.5.post3、NVIDIA Dynamo 0.7.0.post1；指标为 average/P95 job delay 与 JPS；敏感性分析覆盖 max batch size 与 chunk size；消融覆盖 TTL/调度/offload 各组件。
- **论文报告结果（附条件）**：摘要称 "improves the average job completion times by **over 8x** while improving throughput"（SWE-Bench、BFCL、OpenHand；Llama-3.1 8B/70B、Gemma-3 12B、GLM-4.5 355B）；§1 贡献列表称 "up to **8.18x**"。**正文 Figure 8–14 中可读出的倍数为 1.3×–3.7×**，8.18× 对应的具体配置未在正文中标明（未核验项）。
- **局限与范围**：
  - 保留与解除保护以**请求的 KV 缓存**为单位，不区分同一请求内不同块的重算价值；
  - TTL 依赖 inter-request interval 历史，冷启动、分布变化与长尾都会影响估计质量；
  - **未定义块级 victim selection**，逐出本身交给底层引擎；
  - 论文基线是 vLLM **0.10.2**，与本项目 vLLM **0.27.1** 相隔多个大版本。
- **与本项目的关系**：这是 **Baseline 2 / A0 的来源**。按 [`docs/baseline-freeze.md`](../baseline-freeze.md)，项目实现的是**适配到 vLLM 0.27.1 的 Continuum 风格基线**，**不是**源码级精确复现。两处必须显式声明的项目适配：
  1. **压力释放顺序**：论文是 *latest program arrival time*（死锁预防），项目 A0 冻结的是 *earliest retention deadline first → native LRU rank as tie-breaker*，`baseline-freeze.md` §8 明确其为 "an adaptation, not a claimed native Continuum rule"；
  2. **无原生 pin API**：项目用"独立保护表 + 驱逐候选过滤"适配，禁止用抬高 `ref_cnt`、隐藏池或复制 BlockPool 记账来模拟 pin。
  Continuum 的主要输出是每个程序/会话的 TTL，而非对全部可逐出块的统一排序——这正是本项目 Block 层（L1）研究的空间。

#### 2.C.2 SAGA —— L1 + L2 + L4 + L6（三层叠加的系统，不是 Continuum 的变体）

- **研究问题**：请求级调度忽视**工作流原子性**，导致工具调用间隙的 KV 缓存重建与亲和性损失。
- **系统上下文与负载**：**分布式集群**：8 节点 × 8×A100-80GB（共 64 GPU、5.12TB 显存），Ray + gRPC 协调器（P99 worker-to-coordinator < 5 ms）；实现为 vLLM **0.6.0** 扩展（约 8.5K 行 Python + 1.2K 行 C++/CUDA）；Llama-3-70B-Instruct TP=4；SWE-bench **500 verified 任务**（mean 37 steps, max 150；每步 2–4K prompt / 100–500 output）、WebArena **全部 812 任务**（mean 18 steps；每步 4–8K prompt / 50–200 output）、BurstGPT 衍生的 10 租户合成负载。**SWE-bench 与 WebArena 是任务定义而非到达 trace**，按 Poisson λ≈8 tasks/min 单租户重放。每实验 **10 次重复**，Welch's t-test，剔除 3 次 warm-up 与 1.5×IQR 外点（<2%）。
- **主要决策层**：**L4 调度 + L2 TTL + L1 驱逐排序（WA-LRU）+ L6 集群协调**，四层叠加。
- **核心机制**：
  - **AEG（Agent Execution Graph）**：由编排框架 hint（LangChain callbacks、AutoGen message logs）或 §3.3 pattern inference 构建；pattern inference 准确率 87%，相对显式 hint 退化 15.6%，仍相对 vLLM v0.6.0 有 2.60× 加速；
  - **Tool-Call-Aware TTL**：基础值取特定工具类型预期时延的 **p 分位数（默认 p=95%）**，**显存压力大时按比例缩短**，上限 `TTL_max = 300s`；过订阅（>95%）优雅退化为标准 LRU；
  - **WA-LRU**：三个归一化因子（AEG 预测的未来复用概率、新近度、缓存大小）构成逐出分数；
  - **session-affinity batching + work stealing**、**Agent Fair Share** 公平性指标。
- **信号与元数据**：工具类型历史时延分位数；显存压力因子；AEG 预测复用概率；新近度；缓存大小。
- **决策粒度**：工作流任务 / agent 会话 / KV 块（WA-LRU）。
- **信息需求**：**需要 AEG**——要么编排框架提供 hint，要么由历史请求 trace 做 pattern inference。
- **评估方法**：TCT（任务完成时间）、GPU 显存利用率、吞吐、SLO 达成率；与 Bélády 离线最优对照；逐组件消融（Table 4）；多租户公平性；系统开销；参数敏感性。
- **论文报告结果（附条件，必须随数字引用）**：
  - 相对 **vLLM+APC v0.15.1**（含 affinity routing）：SWE-bench TCT 降低 **1.73×±0.11**、WebArena **1.55×±0.09**，**几何均值 1.64×**，p<0.001；GPU 显存利用率提升 1.22×；SLO 达成率 99.2%；
  - 相对 **vLLM v0.6.0**：SWE-bench **3.01×±0.16**、WebArena 2.17×；
  - Figure 1（32×A100、SWE-bench、10 次重复）：vLLM v0.6.0 有 **38% 执行时间**花在重建被丢弃的 KV 缓存上（SAGA 降至 8%，−30pp）；GPU 显存利用率平均 **42%**（Figure 1b 表述为"浪费 58% HBM"，SAGA 达 71%）；端到端时延相对 inference-only 基线 vLLM **6.0×**、+APC **3.5×**、SAGA **1.5×**；
  - Table 2（生产 trace，与 Bélády 最优的接近程度，**1.0 = 最优**，不是时延加速比）：Standard LRU **2.84 / 2.12 / 2.48**（SWE-bench / WebArena / Mean）；LRU + Prefix (vLLM v0.5) **1.97 / 1.74 / 1.86**；WA-LRU (ours) **1.31 / 1.28 / 1.30**；
  - 代价：相对吞吐最优的批调度，**峰值吞吐低约 30%**（纯 BFS 12.4 tasks/min 但逐出率 78%；SAGA TCT 203.4s）。
- **局限与范围**：需要 AEG 或推断模块，且是**分布式调度系统**；WA-LRU 的分数**不直接以候选块的逐出代价为输入**；其负载是合成 Poisson 到达，不是原始 SWE-bench serving trace。
- **与本项目的关系**：**不复现为基线**（需要 AEG + 分布式调度）。两点设计参考：
  1. "显存压力缩放 TTL" 是 L1/L2 耦合的先例——本项目 Block 层的"当前缓存压力"分量可参照；
  2. "复用概率 + 缓存属性构成排序分" 与 Block Idea 2 同构，但**信号来源不同**（AEG vs 本地运行时历史）。
  **不得**把 SAGA 与 Continuum 当作可互换的同类系统：SAGA 是集群级 workflow-atomic 调度 + 自带逐出排序；Continuum 是单机 TTL 保留 + 程序级 FCFS。

### 2.D 类四：面向 LLM-agent 的缓存管理（KVFlow、CacheWise）

> 这一类与类三的差别在于**信号来源**：类三用在线运行时统计（Continuum）或工作流结构（SAGA），类四分别用**工作流执行距离**（KVFlow）与**工具调用元数据**（CacheWise）。

#### 2.D.1 KVFlow —— L1 + L5 + L4（工作流执行距离驱动）

- **研究问题**：多智能体工作流中各 agent 由固定提示初始化、前缀高度重叠，但现有系统按 LRU 逐出，导致缓存未命中与换入停顿。
- **系统上下文与负载**：原型基于 **SGLang v0.4.4**（backend 用 radix tree 管理前缀缓存），改 frontend 与 backend 以传递 agentic workflow 信息；合成工作流 + **PEER 风格**工作流（四 agent：Planner/Executor/Expresser/Reviewer 等）；单工作流 10 agent；两种配置——A10G 24GB + Llama-3.1-8B、H100 + Qwen2.5-32B；与 **SGLang w/ HiCache**（层次化 radix cache）和 GPU-only SGLang 对比。
- **主要决策层**：L1 驱逐优先级 + L5 预取 + L4 状态感知调度。
- **核心机制**：
  - **Agent Step Graph（ASG）** 与 **steps-to-execution**（agent 距未来被激活还有多少步），用 step aggregation 函数（Max/Min +1）在依赖边上计算，表达同步屏障与 AND/OR 条件分支（§3 引言与 Figure 3(a)）；
  - **驱逐优先级传播**（§3.1）：按 steps-to-execution 在缓存树上传播；多 agent 输入的节点取子节点中**最低（最保守）**的优先级，保证**共享节点只要对任一 agent 在不久的将来有用就被保留**（Figure 3(b)）；
  - **重叠 KV 预取**（§3.2）：后台线程把下一步调度到的 agent 所需张量从 CPU 预取到 GPU。
- **信号与元数据**：ASG 结构、steps-to-execution、共享前缀关系。
- **决策粒度**：**KV node**（含树状结构中的共享前缀节点）。
- **信息需求**：**需要工作流结构与 agent 依赖/激活关系**。**这是关键限制：本项目在真实驱逐时刻不一定能获得这类信息。**
- **评估方法**：单工作流时延（固定/动态部分与输出 token 配比扫描）、高并发工作流性能、PEER 风格 token 分布。
- **论文报告结果（附条件）**：相对带层次化 radix cache 的 SGLang，单一大提示工作流最高 **1.83×** 加速，多并发工作流场景最高 **2.19×** 加速。另：Figure 2(b) 显示 PCIe 传输时间远低于重算时间（对照对象是 CPU 卸载路径）。
- **局限与范围**：依赖工作流执行信息；**预取机制与本项目研究的驱逐是不同问题**，不应混为一谈。
- **与本项目的关系**：
  - 对 **Block Idea 1**：提供"何时值得偏离 LRU"的信号族候选——工作流/未来执行距离；能否在本项目驱逐时刻可用需单独验证，不能默认可用；
  - 对 **Block Idea 2**：与 Continuum 的在线运行时信号**不同来源**的信号族。Continuum 是在线观察量（请求间隔、排队延迟、工具统计），KVFlow 是结构化的静态/半静态工作流距离，二者不能互相替代，也不必然相关；
  - Figure 3(b) 的共享节点画法可用于 Entry Idea 4 的共享所有权说明，但**须标注差异**：KVFlow 调整的是驱逐优先级，本项目讨论的是保护释放粒度。

#### 2.D.2 CacheWise —— L1 + L4（工具元数据驱动的复用预测）

- **研究问题**：coding agent 负载（LLM 生成与外部工具调用交替的长时闭环会话）下 KV 缓存复用不足；此类负载的 serving 行为此前未被系统研究。
- **系统上下文与负载**：**vLLM 实现**（约 2,500 行 Python，扩展 batch scheduler 与 KVCache manager）；2×H200（TP=2，共 282GB）、AMD EPYC 9534 64 核；**Qwen2.5-Coder-32B-Instruct**；自采 **CATraces**（80% 会话离线训练预测器，其余做实验）；并发 N 个会话，N≤10 低负载、N>10 高负载。
- **主要决策层**：L4 前缀感知调度 + L1 复用感知驱逐。
- **核心机制**（论文分三部分，**不应笼统概括为"使用工具元数据"**）：
  - **§3 Coding Agent Workloads**：负载画像（会话结构、上下文增长、轮次分布、工具触发请求 CDF）；报告**工具元数据（工具类型与参数）能捕捉执行行为的有意义结构**；
  - **§4 Implications**：从负载特征推出优化机会；
  - **§5 CACHEWISE Design**：`§5.1 Prefix-aware Request Scheduling`（按与 XPU 常驻 KV 的重叠度排序请求）+ `§5.2 Predictive KVCache Eviction`（块带 `tool_name`/`tool_args`/`T_i` 元数据进逐出堆，轻量预测器估 `E[τ_i(t)]`；对工具参数做 TF-IDF 嵌入 + KMeans 聚类，用簇内分布代替按工具分布；`N_rebuild=3` 周期性重估）+ `§5.3 Implementation`。
- **信号与元数据**：工具调用元数据（工具类型、参数）及其派生的复用预测；距上次访问时间。
- **决策粒度**：前缀 / 块。
- **信息需求**：工具调用元数据来自 agent 框架的可观测事件。
- **评估方法**：token goodput、请求吞吐、请求/会话完成时间（**会话完成时间不含工具执行时长**）、KV 搬移量；基线为 **vLLM（block-level LRU + FCFS）** 与 **InferCept（FCFS + moving-average 驱逐）**；消融含 CACHEWISE*（用 ground-truth 工具时延）、vLLM(Prefix-aware)、InferCept(Prefix-aware)。**论文明确说未直接与 SGLang 对比。**
- **论文报告结果（附条件，必须分层引用）**：
  - 摘要/结论：KV 驱逐次数减少最多 **2–2.6×**，端到端会话完成时间改善最多 **~3.5×**；
  - §6.2：N>10 时相对 vLLM 与 InferCept 为 **2.7×–3.5×** 更低完成时间，且与 CACHEWISE*（ground truth）相当；
  - **分量拆分**：单独看预测式驱逐只有 **~1.7×–2×**（相对已加前缀感知调度的基线，token goodput 高 1.2×–1.6×）；前缀感知调度单独贡献 **~1.8×–2.66×**（token goodput 高 ~1.38×–1.7×）。
- **局限与范围**：§1 写 "total **request** completion time"、结论写 "end-to-end **session** completion time"，论文自身口径不一致；预测器假定系统常规记录请求 trace 可作训练数据，未研究分布漂移；`XPU` 是论文自定的容量单位，不可与本项目块数直接换算。
- **与本项目的关系**：
  - 与 Continuum 的联系在于两者都从工具调用历史派生信号，但**用途不同**：Continuum 的工具间隔统计用于估计 **TTL（保留多久）**，CacheWise 的工具元数据用于**预测复用并指导驱逐排序**；
  - 对 **Block Idea 2**：说明工具元数据作为复用预测信号在 coding agent 负载上有论文级支持，值得在本项目中检验；
  - **不得**假设其所有信号已被本仓库实现或可直接用于 Block selector：本项目 `ExternalToolDurationHistory` 当前**只写不读**（`src/` 内无消费者，仅测试断言读取其写入结果），请求间隔样本只进 TTL 估计器，均未到达 Block 驱逐决策点；
  - **不得**把 3.5× 当作驱逐算法的贡献——按论文自己的拆分，它主要是调度 + 驱逐的合成果。

### 2.E 类五：关于"复杂驱逐更优"的系统性反向证据

#### 2.E.1 When Fancy Eviction Fails（WFEF）—— L1

- **研究问题**：几十年的传统缓存管理技术能否直接迁移到 agentic / 对话式 LLM serving？
- **系统上下文与负载**：两条生产 trace——**FreeInference Trace**（327.5K 请求 / 10.5B token / 7.0 天 / 34.3% 请求属于多轮会话）与 **Chutes Trace**（515.8K 请求 / 9.7B token / 130.9 天 / 26.1%），合计**超过 200 亿处理 token**；请求上限 256K token；块身份 16 token 细粒度；自建模拟器 + 生产 trace 回放 + 真实 GPU 测量（Qwen3-Coder-30B、H200 48GiB、B200 96GiB、vLLM）。
- **主要决策层**：**L1 驱逐算法本身**（跨 HBM 与内存池两种机制）。
- **核心机制**：评估 **14 种在线驱逐算法**（§3.2 按设计原则分组：recency 的 LRU；quick demotion 的 ARC / Sieve / S3-FIFO / S4-FIFO / LIRS；analytic modeling 的 LHD；frequency 的 LFU / W-TinyLFU；learned 的 LeCaR / LRB / 3LCache；domain-specific 的 Workload-aware / AsymCache），并以 **Belady's optimum 作为离线 ceiling**（不属于 14 种在线算法）；附录 A 的密集扫描因 LRB 过慢而排除它。提出三项设计原则——**quick demotion**（§5.1，过滤一次性提示）、**compute-aware eviction**（§5.2，优先处理昂贵 miss，含 partial-node 驱逐）、**capacity-adaptive eviction granularity**（§5.3，Block-Level vs Session-Level）。
- **信号与元数据**：recency、frequency、以及上述三项原则；**无需先验工作流信息**。
- **决策粒度**：块 / 会话级（§5.3 的对照）/ partial-node（§5.2）。
- **信息需求**：无外部工作流信息。
- **评估方法**：容量受限 per-replica HBM（**24–120 GiB/GPU**：Table 2 给出 24 GiB = 16,384 块（native-context floor）、48 GiB = 32,768 块（1×H200 @0.8 memory fraction）、96 GiB = 65,536 块（1×B200 bf16））与全局内存池（**0.25–12 TiB**：1 TiB = 699,051 块 = Mooncake 整节点）两种机制；块命中率、compute-savings ratio、与 BeladyCompute 离线上界的距离；TTFT 与 prefill 吞吐；附录 A 做 65 个容量的密集扫描，附录 B 做并发度敏感性，附录 C 用理想线性成本模型，附录 D 报告重算碎片化。
- **论文报告结果（附条件）**：
  - 简单 LRU **出乎意料地稳健**，与复杂传统策略表现相当（**频率类算法往往更差**）；同时距 Bélády 最优仍有可观剩余空间；
  - **结构性原因**：前缀复用由**活跃会话的稳定节奏**主导，使 recency 成为异常强的预测因子；
  - **前缀缓存与传统负载的差异**：单轮请求普遍、会话足迹极度倾斜（§4.5，中位每会话仅 45 块、重尾）、miss cost 因注意力计算随 token 深度增长而**高度非均匀**（§4.4）；
  - **反例（引用时必须同时给容量与 trace）**：Figure 11 在 **24 GiB** 的 Qwen To-B 上 S3-FIFO 与 ARC 达 **0.491**、LRU 为 **0.403**——说明"LRU 稳健"依赖容量与负载，不得概括为"LRU 普遍最优"；
  - 附录 A：quick demotion 的收益随容量增长可能**反转**（Qwen To-C 上 LIRS 从高于 LRU 4.2 点变为低于 10.1 点 @724GB）；W-TinyLFU 对缓存大小**非单调**（FreeInference 上 0.866@97GB → 0.759@906GB → 0.933@12TB）。
- **局限与范围**：容量点、硬件、模型与 trace 均为论文自定，**不可直接照搬到本项目**；命中率类结果主要来自自建模拟器与 trace 回放，只有 Figure 7/8/13 报告真实 GPU/vLLM 测量（引用时须区分两类证据）。
- **与本项目的关系（**这是本项目最重要的反向证据来源**）**：
  - **Block Idea 1**：把"何时值得偏离 LRU"作为**可检验问题**，而不是预设复杂策略更好；
  - **Block Idea 2**：必须验证中间信号相对 TTL/deadline proxy 的**增量**价值；
  - **Entry Idea 3**：必须检验复杂释放顺序相对简单规则的**实际改进**，而不是只证明规则之间存在差异；
  - **Entry Idea 4**：必须检验部分解除保护的收益是否足以抵消实现复杂度，以及其优势是否依赖容量、前缀共享结构与 miss cost 分布；
  - **不得**把该论文的实验结果当作本项目的实验结论，也不得仅根据标题推断其方法。

## 3. 研究定位与研究缺口

### 3.1 本项目要评估什么

本项目**不再扩充策略实现**。当前目标是在受控的真实 vLLM 0.27.1 + GPU APC 环境下，严谨评估**已存在的实验臂**：

| 臂 | Entry forced release | Physical block victim selection |
| --- | --- | --- |
| A0 | 冻结的 Continuum 风格确定性基线 | 现有 eligibility 下的 native LRU |
| A1 | cost-aware Entry 级选择 | 与 A0 相同的 Block 层基线 |
| A2 | A0 的 Entry 级释放 | cost-aware Block 级 selector |

`A2` **不是** A1+A2 的联合策略。A1 与 A0 的差异本身**不能**建立 A1 的 q/λ/pair-lookahead 信号的独立价值；任何未来正式结论都必须包含 **`Sufficient-first + earliest-deadline`** 这一强比较对象。状态与门禁以 [`docs/research-status.md`](../research-status.md) 为准。

### 3.2 文献支持的定位（谨慎表述）

| 论断 | 文献支持 | 强度 |
| --- | --- | --- |
| 分页块管理使块级驱逐决策成为可能 | PagedAttention（L0） | 直接、机制性 |
| "自适应"不等于"感知逐出代价" | ARC：频率维度仍只预测"会不会再被访问" | 机制性对比，非性能对比 |
| "比 LRU 好"不一定需要成本模型 | RLT：随机化在其模型下把竞争比从 O(n) 改善到 O(log n) | 理论性，条件依赖强 |
| Agent 挂起期的保留决策已被系统研究，但**输出是 TTL 而非块级排序** | Continuum（L2/L3/L4，无 L1 策略） | 直接，可核验 |
| 工作流结构可驱动逐出优先级，但**依赖 AEG/ASG** | SAGA（AEG）、KVFlow（ASG） | 直接 |
| 工具元数据可作为复用预测信号 | CacheWise §5.2 | 直接，但收益主要是调度+驱逐合成果 |
| **复杂驱逐不一定优于 LRU** | WFEF：14 种算法、>200 亿 token，LRU 出乎意料地稳健 | 直接，但**存在容量/负载相关的反例**（24 GiB Qwen To-B 上 ARC/S3-FIFO 0.491 vs LRU 0.403） |

### 3.3 研究缺口的谨慎表述（不得过度断言）

**可以说的**：

- 在本次核验的 8 篇文献中，Continuum 的保留与解除保护以**请求/程序前缀**为粒度，论文未给出块级 victim selection；SAGA/KVFlow/CacheWise 的逐出排序分别依赖 **AEG**、**ASG**、**工具调用元数据**三类本项目在驱逐时刻不一定可获得的信息。
- 本项目要检验的是一个**可被证伪的问题**：在只使用本地运行时信号的约束下，改进 Entry 释放顺序与 Block 受害者选择能否带来可测量的决策与结果变化。

**不能说的**：

- ❌ "没有现有工作考虑过成本感知驱逐"——WFEF 的 §5.2 compute-aware eviction、SAGA 的 WA-LRU 复用概率、CacheWise 的 `E[τ]` 预测都含代价/价值估计成分。**该全称否定命题未在相关文献上验证过，不得使用。**
- ❌ "复杂驱逐更优"或"复杂驱逐无效"——WFEF 自身同时给出"LRU 稳健"的主结论和 24 GiB 下复杂策略反超的反例。
- ❌ "Continuum 是 LRU 变体"或"SAGA 与 Continuum 可互换"——二者决策层、粒度、信息需求与系统形态都不同（见 [`对比笔记.md`](References&Notes/对比笔记.md)）。
- ❌ 把任何论文的性能数字说成本项目实测或预期。

## 4. 范围边界

- 不改注意力内核；不做多卡与分布式；不做 CPU KV offloading；不复现 PagedAttention / vLLM 本身；
- 不复现 ARC、RLT/LBGR、SAGA、KVFlow、CacheWise 的完整系统；
- Continuum 风格基线复现其动态 TTL / retention 与程序级调度决策逻辑，不复现其完整系统，也不声称与论文逐行等价；
- 完整排除清单见 [`docs/baseline-freeze.md`](../baseline-freeze.md) 的 Explicit First-Version Exclusions；
- 四个优化方向（Block Idea 1/2、Entry Idea 3/4）是**潜在未来研究方向，不属于冻结的 Phase 3 评估战役**；其评分函数、信号权重、介入阈值与 partial-tail 规则**尚未冻结**，一律保持 proposal / hypothesis 定位，不得写成已批准的实施任务。逐方向的实现状态与评估边界见 [`kv_cache_optimization_motivation_and_design_proposal.md`](kv_cache_optimization_motivation_and_design_proposal.md) §3 状态矩阵。
