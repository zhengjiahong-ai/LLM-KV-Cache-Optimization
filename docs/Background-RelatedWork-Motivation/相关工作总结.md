# 相关工作总结

> **文档定位**：本项目相关工作的结构化总结。每篇工作按「解决什么问题 → 决策层级 → 使用的信号 → 需要的外部信息 → 适用场景 → 与本项目的关系」组织，不做"某某论文没有成本感知"式的笼统归类。
>
> **当前研究主线**：以 Continuum 风格 retention/unpin 机制的项目适配与验证为基础，研究如何改进 **Entry 级保护释放决策**，并设计与其适配的 **Block 级物理驱逐算法**，最终评估两层各自及协同的价值。四个研究方向见 [`kv_cache_optimization_motivation_and_design_proposal.md`](kv_cache_optimization_motivation_and_design_proposal.md)，动机叙述见 [`项目动机文档.md`](项目动机文档.md)。
>
> **状态来源**：[`docs/research-status.md`](../research-status.md)。逐篇文献细节见 `References&Notes/论文总结.md`，横向对比见 `References&Notes/对比笔记.md`，术语口径见 `专业术语表.md`。

## 1. 决策层级：先分清各工作改的是哪一层

相关工作的差异首先在**决策层级**，而非策略本身的复杂度。本项目关注的两个层级是：

| 层级 | 决策内容 | 本项目代码位置 |
| --- | --- | --- |
| Entry 级 unpin / pressure release | 压力下释放哪些 Entry 的保护，使其关联 Block 获得被回收**资格** | `src/kvopt/continuum/pressure.py` |
| Block 级 physical eviction | 在可驱逐候选中最终移除哪些物理块 | `src/kvopt/runtime/vllm/adapter.py`、`src/kvopt/costaware/a2_native.py` |

此外还有两个容易混淆的层级：**保留时长**（TTL/租约）与**调度**（请求执行顺序）。一篇论文可以只动其中一层，也可以多层叠加；比较时必须对齐层级。

## 2. 逐篇梳理

### 2.1 PagedAttention / vLLM —— 运行载体，不是被比较的策略

- **解决什么问题**：连续内存分配造成的内部/外部碎片。论文报告传统系统 KV 缓存有效内存利用率可低至 **20.4%**。
- **决策层级**：内存布局与块管理，不定义驱逐策略本身。
- **使用的信号**：块表、哈希、`ref_cnt`。
- **需要的外部信息**：无。
- **适用场景**：所有分页 KV 缓存系统。
- **与本项目的关系**：本项目跑在 vLLM 0.27.1 + GPU APC 上，不修改该机制。vLLM 0.6.0 文档记载的前缀缓存逐出语义（只考虑 `ref_cnt = 0` 的块；多个候选时优先最久未使用；时间相同则优先最长前缀末端）可作为"vLLM 风格 LRU"的语义参考，但不等同于当前所有版本的默认行为。详见 `References&Notes/参考文献/关于vLLM的参考文档与网址.md`。

### 2.2 ARC（Recency/Frequency Adaptive）—— 自适应空间配比，不含逐出代价

- **解决什么问题**：LRU 只看新近度，不相关负载互相冲刷缓存。
- **决策层级**：驱逐 + 两类队列的空间配比。
- **使用的信号**：新近度、频率、幽灵缓存反馈。
- **需要的外部信息**：无。
- **适用场景**：访问模式可分的负载。
- **与本项目的关系**：说明"自适应"仍不等于"感知逐出代价"——它判断"块是否会被再次访问"，不判断"被逐出后再次访问需要多大的重算代价"。作为机制对照，不复现为基线。

### 2.3 RLT + LBGR —— 随机化与路由，成本估计发生在路由侧

- **解决什么问题**：LRU 对动态在线查询脆弱，且缓存亲和与负载均衡目标冲突。
- **决策层级**：驱逐（RLT，叶子 token 内随机）+ 请求路由（LBGR）。
- **使用的信号**：随机性（RLT）；端到端延迟估计（LBGR）。
- **需要的外部信息**：论文模型下的前缀共享与到达顺序假设。
- **适用场景**：论文设定的动态/对抗性到达。
- **与本项目的关系**：其理论结果（在其前缀共享与到达顺序模型下，Leaf-LRU 最坏竞争比 \(O(n)\)，RLT 改善到 \(O(\log n)\)）说明"比 LRU 好"不一定需要成本模型；因此本项目必须用消融证明收益来自成本信号本身。其延迟估计公式（服务时间 + 队列负载 + 残差校正）对多维在线估计有方法启发。不复现为基线。

### 2.4 Continuum —— 保留时长与压力释放，是本项目的基线与设计来源

- **解决什么问题**：Agent 工具调用期间 LLM 暂停，end-of-turn eviction 会丢弃随后就要用的 KV 缓存，并造成逐出后的排队延迟。
- **决策层级**：保留时长（TTL）+ 软保护/解除保护 + 程序级调度。
- **使用的信号**：服务端请求间隔历史样本、排队延迟、预填充重算开销、轮次记忆度因子 `eta`。TTL 在离散候选集 `{0} ∪ 已观测时长` 上按经验 CDF 枚举，最大化 `P(τ,f)·(Tη + PrefillReload) − τ`。
- **需要的外部信息**：程序/会话身份与工具事件由 workload/orchestrator 提供；vLLM 不原生提供。
- **适用场景**：多轮 Agent 负载（论文在 SWE-Bench、BFCL、OpenHand 上评估）。
- **论文报告的性能**：摘要称在真实 Agent 上"improves the average job completion times by over 8x while improving throughput"（模型含 Llama-3.1 8B/70B、Gemma-3 12B、GLM-4.5 355B）。**这是论文作者的结论与其实验条件，不是本项目实测，也不构成本项目预期收益。**
- **与本项目的关系**：这是 Baseline 2 / A0 的来源。按 [`docs/baseline-freeze.md`](../baseline-freeze.md)，项目实现的是**适配到 vLLM 0.27.1 的 Continuum 风格基线**，**不是**源码级精确复现；复现范围聚焦决策逻辑，不含完整系统。Continuum 的主要输出是每个程序/会话的 TTL，而非对全部可逐出块的统一排序——这正是本项目 Block 层研究的空间。

### 2.5 SAGA —— 工作流感知的保留与逐出

- **解决什么问题**：请求级调度忽视工作流原子性，导致 KV 缓存重建与亲和性损失。
- **决策层级**：调度 + TTL 调整 + 驱逐排序（WA-LRU），三层叠加。
- **使用的信号**：工具类型历史延迟分位数定 TTL；显存压力因子缩短 TTL；WA-LRU 用 AEG 预测的未来复用概率 + 新近度 + 缓存大小排序。
- **需要的外部信息**：AEG（可由编排框架提示提供，或由历史 trace 推断）。
- **适用场景**：GPU 集群上的 Agent 工作流。
- **论文报告的性能**（条件必须随数字一起引用）：在其 64 张 A100-80GB（8 节点 × 8 卡）集群上，相对 **vLLM v0.15.1 + APC**，SWE-bench 任务完成时间降低 **1.73×±0.11**（p < 0.001），WebArena 1.55×±0.09；相对 vLLM v0.6.0 则为 3.01×。另在 32 张 A100、vLLM v0.6.0、10 次重复的 SWE-bench 实验中报告 Agent 有 **38% 总时间**用于重建被丢弃的 KV 缓存，GPU 显存利用率平均 42%；其引用的 Agent 会话 KV 缓存规模为 **2–12 GB/请求**（条件：32K 上下文、70B 级模型、GQA）。
- **与本项目的关系**：不复现为基线（需要 AEG 或推断模块，且含分布式调度）。其"显存压力缩放 TTL"与"复用概率 + 缓存属性构成排序分"对本项目 Block 层信号设计有参考价值；本项目拟只使用本地运行时历史，不接入 AEG。

### 2.6 KVFlow —— 工作流执行距离驱动的前缀缓存管理

- **解决什么问题**：多智能体工作流中，各 agent 由固定提示初始化、前缀高度重叠，但现有系统按 LRU 逐出，导致缓存未命中与换入开销。
- **决策层级**：Block/KV-node 级驱逐优先级 + 预取 + 调度。
- **使用的信号**：**Agent Step Graph** 与 **steps-to-execution**（agent 距未来被激活的步数），按步聚合函数在图上传播驱逐优先级；共享节点取所有依赖 agent 中最低（最保守）的优先级，以保留树状结构中的共享前缀。
- **需要的外部信息**：工作流结构（Agent Step Graph）与 agent 间的依赖/激活关系。**这是关键限制：本项目在真实驱逐时刻不一定能获得这类信息。**
- **适用场景**：结构化多智能体工作流（论文用合成与 PEER 风格工作流评估）。
- **与本项目的关系**：
  - 对 **Block Idea 1**：提供了一个"何时值得偏离 LRU"的信号族候选——工作流/未来执行距离；但它依赖工作流执行信息，能否在本项目驱逐时刻可用需单独验证。
  - 对 **Block Idea 2**：是与 Continuum 在线运行时信号**不同来源**的信号族。Continuum 的信号是在线观察量（请求间隔、排队延迟、工具统计），KVFlow 的信号是结构化的静态/半静态工作流距离。二者不能互相替代，也不必然相关。
  - 其预取机制（把 CPU 上的 KV 预取到 GPU）与本项目研究的驱逐问题是不同问题，不应混为一谈。
  - **不得**把 KVFlow 论文报告的性能结果当作本项目的预期收益。

### 2.7 CacheWise —— Coding Agent 负载特征与工具元数据驱动的复用预测

- **解决什么问题**：coding agent 负载（LLM 调用与外部工具调用交替）下 KV 缓存复用不足。
- **决策层级**：前缀感知调度 + 复用感知驱逐（论文称 reuse-aware eviction guided by lightweight predictions from tool call metadata）。
- **使用的信号**：工具调用元数据（论文 §3 报告工具类型与参数等工作负载元数据能捕捉执行行为的有意义结构，可用于复用预测信号）。
- **需要的外部信息**：工具调用元数据来自 agent 框架的可观测事件。
- **适用场景**：coding agent 负载；论文基于其采集的 CATraces。
- **论文报告的性能**：摘要称在 vLLM 中实现后，KVCache 驱逐次数减少最多 2–2.6×，总 agent 会话完成时间改善最多约 3.5×。**这是论文作者的结论与其实验条件，不是本项目实测。**
- **与本项目的关系**：
  - 与 Continuum 的联系在于两者都从工具调用历史派生信号，但**用途不同**：Continuum 的工具间隔统计用于估计 TTL（保留多久），CacheWise 的工具元数据用于预测复用并指导驱逐排序。
  - **不得**把 CacheWise 的全部设计笼统概括为"使用工具元数据"；其负载特征分析、预测式驱逐机制与评估是分开的部分，分别见论文 §3、§5.2、§6。
  - **不得**假设其所有信号已被本仓库实现或可直接用于 Block selector：本项目 `ExternalToolDurationHistory` 当前**只写不读**（`src/` 内无消费者，仅测试断言读取其写入结果），请求间隔样本只进 TTL 估计器，均未到达 Block 驱逐决策点。

### 2.8 When Fancy Eviction Fails —— 对"复杂驱逐更优"的系统性反向证据

- **解决什么问题**：传统缓存管理技术能否直接迁移到 Agent/对话式 LLM serving？
- **决策层级**：驱逐算法本身（跨 HBM 与内存池两种机制）。
- **使用的信号**：recency、frequency、以及论文提出的 quick demotion、compute-aware eviction、capacity-adaptive eviction granularity。
- **需要的外部信息**：论文使用生产 trace 与自建模拟器，无需先验工作流信息。
- **论文报告的结果与条件**：在超过 200 亿 token 的生产 trace 上评估 14 种驱逐算法，报告简单 LRU 出乎意料地稳健、与复杂传统策略表现相当（频率类往往更差）；原因是结构性的——前缀复用由活跃会话的稳定节奏主导，recency 是异常强的预测因子。同时指出前缀缓存与传统负载的差异：单轮请求普遍、会话足迹极度倾斜、miss cost 因注意力计算随 token 深度增长而高度非均匀。
- **与本项目的关系（这是本项目最重要的反向证据来源）**：
  - **Block Idea 1**：把"何时值得偏离 LRU"作为可检验问题，而不是预设复杂策略更好；
  - **Block Idea 2**：必须验证中间信号相对 TTL/deadline proxy 的**增量**价值；
  - **Entry Idea 3**：必须检验复杂释放顺序相对简单规则的**实际改进**，而不是只证明规则之间存在差异；
  - **Entry Idea 4**：必须检验部分解除保护的收益是否足以抵消实现复杂度，以及其优势是否依赖容量、前缀共享结构与 miss cost 分布。
  - **不得**把该论文的实验结果当作本项目的实验结论，也不得仅根据标题推断其方法。

### 2.9 vLLM RFC #37003 —— 工程接口提案

- **解决什么问题**：让上层编排器为 token 范围声明保留优先级与时长。
- **决策层级**：保留指令接口（自顶向下由调用方声明重要性）。
- **与本项目的关系**：与本项目"由系统在线估计重要性"的路线互补。该提案的存在说明问题已受社区关注。
- **状态与证据等级**：这是 RFC/工程提案，**不是同行评审论文，不得作为性能收益证据**。仓库参考笔记记载其标题为 "Context-Aware KV-Cache Retention API (Prioritized Evictions)" 且当时为 Open 状态。

## 4. 相关工作如何支撑四个方向

| 方向 | 主要相关工作 | 支撑方式 | 边界 |
| --- | --- | --- | --- |
| Block Idea 1（介入门槛） | WFEF、vLLM 原生 LRU、A2 已有回退路径 | 提供"复杂策略未必更优"的反向证据与真实基线定义 | 不得据论文结论预设本项目策略无效或有效 |
| Block Idea 2（中间信号） | Continuum、CacheWise、KVFlow | 提供三类不同来源的信号族与各自的可用性约束 | 只有 deadline 当前到达 Block 层；`ExternalToolDurationHistory` 只写不读 |
| Entry Idea 3（unpin 排序） | Continuum 压力释放、SAGA 的 TTL 压力缩放 | 提供冻结 A0 顺序的上文与可比较的简单规则 | A0 已消费 `native_lru_rank`；A1 的 54/54 复现是直接警示 |
| Entry Idea 4（unpin 粒度） | WFEF 的 compute-aware / capacity-adaptive granularity、KVFlow 的共享前缀处理、vLLM RFC #37003 | 提供部分粒度与共享所有权的设计先例 | 论文的部分粒度讨论不等于本项目的 partial-tail unpin；RFC 不是性能证据 |

## 5. 范围边界

- 不复现 PagedAttention / vLLM 本身，不改注意力内核，不做多卡与分布式；
- 不复现 ARC、RLT/LBGR、SAGA、KVFlow、CacheWise 的完整系统；
- Continuum 风格基线复现其动态 TTL / retention 与程序级调度决策逻辑，不复现其完整系统，也不声称与论文逐行等价；
- 完整排除清单见 [`docs/baseline-freeze.md`](../baseline-freeze.md) 的 Explicit First-Version Exclusions。
