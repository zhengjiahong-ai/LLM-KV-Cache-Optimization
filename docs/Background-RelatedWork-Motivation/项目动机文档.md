## 1. 为什么 KV 缓存对 LLM 推理重要

### 1.1 KV 缓存与预填充重算

【事实】自回归 LLM 在生成每个 token 时都要用到此前全部 token 的 Key/Value 张量。推理系统把这些张量缓存下来，避免对历史上下文重复做前向计算，这就是 **KV 缓存（KV Cache）**。其显存占用随上下文长度、批大小与并发请求数近似线性增长。

【事实】当缓存总量接近 GPU 显存上限时，系统必须在以下动作之间取舍：延后或拒绝新请求、把部分缓存换出到 CPU/远端、或**驱逐（eviction）**部分缓存。被驱逐的内容若再次被请求，必须重新执行计算密集的**预填充（prefill）**，直接抬高首词延迟（TTFT）与请求完成时间。

【解释】因此，驱逐决策的代价不是"少存了一些数据"，而是"未来可能多算多少 token、多等多久"。这正是本项目把**重算代价**作为核心量的原因；但"代价"是否可测、可归因，本身需要严格验证（§8）。

### 1.2 压力下的三类选择

【解释】容量不足时，工程上通常有三类应对，它们的决策层不同：

| 应对 | 改变什么 | 不改变什么 |
| --- | --- | --- |
| 保留 / 保护（retention） | 某段前缀在一段时间内不被普通逐出路径回收 | 不改变物理块的内容或位置 |
| 解除保护 / 压力释放（unpin / pressure release） | 哪些 Block **获得被回收的资格** | 不移动数据、不释放显存 |
| 物理驱逐（eviction） | 哪些已获资格的物理 Block **实际被移除** | 不创造新的资格 |

【事实】本项目运行在真实 **vLLM 0.27.1 + GPU Automatic Prefix Caching（APC）** 上：块按内容哈希共享，`ref_cnt > 0` 的块不可驱逐。项目不修改注意力内核，也不改变 vLLM 的块表、哈希与引用计数记账。

### 1.3 可用于说明问题规模的外部证据（均为论文报告，附条件）

- 【事实】**PagedAttention** 论文报告（其 profiling 实验：13B 模型、NVIDIA A100 40GB），传统连续分配系统的 KV 缓存有效内存利用率可低至 **20.4%**（论文报告范围为 20.4%–38.2%）。这说明分配方式本身就会造成显著浪费；本文引用它只为说明问题规模，**不是**本项目实测。见 [`References&Notes/论文总结.md`](References&Notes/论文总结.md) §1。
- 【事实】**SAGA** 论文报告（32 张 A100-80GB 运行 SWE-bench、vLLM v0.6.0、10 次重复），Agent 有 **38% 的执行时间**用于重新生成工具调用期间被丢弃的 KV 缓存，GPU 显存利用率平均约 42%。这是该论文在其集群与负载下的测量，**不是**本项目结果。见 [`References&Notes/论文总结.md`](References&Notes/论文总结.md) §5。
- 【事实】**When Fancy Eviction Fails** 报告（两条生产 trace、超过 200 亿 token、14 种在线驱逐算法），前缀复用由活跃会话的稳定节奏主导，recency 是异常强的预测因子；同时指出 miss cost 随注意力深度增长而高度非均匀。见 [`References&Notes/论文总结.md`](References&Notes/论文总结.md) §8。

【解释】这些结果共同说明：KV 缓存的容量与保留/驱逐决策会造成可观的重算浪费，值得研究；但它们没有说明"更复杂的策略一定能减少这种浪费"。后者必须通过本项目自己的受控实验来检验。

## 2. 内存压力为什么产生保留与驱逐问题

### 2.1 容量、工作集与驱逐

【解释】只要"活跃会话的可复用前缀工作集"大于可用 KV 容量，系统就必须持续做驱逐决策。此时有三个不同量需要分开：

- **可复用前缀**：按冻结的 eligibility 规则，本来可以被复用的 token 数（记为 `E`）；
- **实际命中**：Native APC 实际从缓存中取到的 token 数（记为 `C`）；
- **重算**：本来可复用、但因内容已不在缓存中而必须重新计算的 token 数（`E − C`）。

【事实】协议冻结的约束是 `0 ≤ C ≤ E ≤ N`（`N` 为原生 prompt token 数）；任何违例都按证据失败处理，不得截断修补。主指标是绝对量 `Σ(E − C)`，而不是归一化比例。见 [Protocol v4 §1](https://github.com/zhengjiahong-ai/LLM-KV-Cache-Optimization/blob/main/docs/phase3-final-evaluation-protocol-v4.md)（`N/E/C` 定义与主指标与 v3 一致；v3 §3 为历史定义）。

### 2.2 多轮与工具调用放大问题

【解释】在多轮 Agent 负载中，LLM 调用与外部工具调用交替进行。工具执行期间模型推理暂停，对应的 KV 缓存暂时无人访问；如果系统在"请求完成"时立即按普通路径回收，随后同一个会话的下一步又要重新预填充整段历史。这种"暂时无人访问即被淘汰、随后立刻需要"的现象，就是 retention 类机制要解决的问题。

【事实】Continuum 论文报告（SWE-Bench、BFCL、OpenHand；Llama-3.1 8B/70B、Gemma-3 12B、GLM-4.5 355B；基线 vLLM 0.10.2），使用工具感知 TTL 与 program-level FCFS 后，平均作业完成时间改善 **over 8x**。这是论文在其负载与系统条件下的结论，**不是**本项目结果，也不构成本项目预期。见 [`References&Notes/论文总结.md`](References&Notes/论文总结.md) §4。

【解释】但 TTL 不是本项目的全部问题。Continuum 的主要输出是"保留多久"；它没有定义块级 victim selection。本项目把"保留/释放"与"物理驱逐"分开研究（§5）。

### 2.3 本项目的运行边界

【事实】真实后端冻结为 **vLLM 0.27.1 + GPU APC**。Continuum 风格基线是**项目侧适配**，不是对论文完整系统的源码级复现：vLLM 0.27.1 没有原生的 program/session 身份、pin API、工具间隔状态与 program-level 调度原语；项目用独立保护表 + 驱逐候选过滤来适配，且不得用抬高 `ref_cnt`、隐藏池或复制 `BlockPool` 记账来模拟 pin。见 [`docs/baseline-freeze.md`](../baseline-freeze.md) §4、§6。

## 3. 为什么 LRU 是强而必要的基线

### 3.1 vLLM 原生 APC LRU 的语义

【事实】vLLM v0.6.0 的实现文档记载：前缀缓存满时只考虑 `ref_cnt = 0` 的块；多个候选时优先逐出最久未使用块；最后访问时间相同则优先最长前缀末端。项目把它作为"vLLM 风格 LRU"的语义参考（v0.6.0 文档，**不等同于** 0.27.1 所有配置的默认行为，也未在 0.27.1 上逐项核验）。见 [`References&Notes/参考文献/关于vLLM的参考文档与网址.md`](References&Notes/参考文献/关于vLLM的参考文档与网址.md) §1。

### 3.2 外部证据：LRU 出乎意料地稳健，但不是普遍最优

【事实】**When Fancy Eviction Fails** 在两条生产 trace（超过 200 亿 token）上评估 14 种在线驱逐算法，报告简单 LRU 与复杂传统策略表现相当，频率类算法往往更差；原因是前缀复用由活跃会话的稳定节奏主导，recency 是很强的预测因子。同时，论文保留了距 Bélády 离线最优的显著 headroom。

【事实】该论文也给出**反例**：在 24 GiB 的 Qwen To-B 上，S3-FIFO 与 ARC 的块命中率为 **0.491**，LRU 为 **0.403**。因此"LRU 稳健"依赖容量与负载，**不得**概括为"LRU 普遍最优"。见 [`References&Notes/论文总结.md`](References&Notes/论文总结.md) §8。

【事实】RLT 论文在其前缀共享与到达顺序模型下给出：Leaf-LRU 最坏竞争比为 `O(n)`，随机化叶子驱逐可改善到 `O(log n)`；其实验基线为 SGLang 的 L-LRU，覆盖 GSP、ShareGPT/UltraChat、Loogle 三类前缀共享负载（Llama-3.1 8B/70B 与 Mixtral 8×7B）。这是**最坏情况**的理论结论，不能直接预测平均性能。见 [`References&Notes/论文总结.md`](References&Notes/论文总结.md) §3。

### 3.3 对项目的含义

【解释】LRU 是必要基线，原因有三：

1. 它是真实系统的默认行为，任何"改进"都必须相对它可测量；
2. 它已经利用了很强的信号（recency），不是一个容易击败的稻草人；
3. 它不需要额外的外部工作流信息，因而在真实黑盒场景中可用。

【假设】"更复杂的成本感知或工作流感知策略一定优于 Native LRU"**不是一个可以预设的前提**，而是一个必须用受控实验检验的假设。本项目的动机正是建立在这个可证伪的立场上，而不是建立在"复杂必然更好"的叙事上。

## 4. 前缀复用与多轮 Agent 负载带来的额外考虑

### 4.1 前缀共享

【事实】APC 通过内容哈希让不同请求共享同一物理 Block。一个物理 Block 可以被多条逻辑前缀链引用；驱逐它会影响所有依赖该前缀的请求。共享前缀（例如固定的系统提示、工具定义、长文档）往往是"重算昂贵"的典型来源。

【解释】共享带来两个后果：第一，**逻辑 Entry 边界不等于物理 Block 所有权边界**；第二，单个 Block 的驱逐代价取决于它处在多深的位置、被多少前缀共用、以及后续请求是否真的会用到它。这使"按块计代价"不能只看块数。

### 4.2 工具挂起期与保留

【解释】多轮 Agent 负载中，工具调用造成的挂起期是"虚假驱逐"的高发窗口：缓存暂时不活跃，但随后很可能被同一会话再次使用。Continuum/TTL 类机制针对这个窗口；但保留多久、保留哪一层、以及释放后下游是否真的会驱逐，都是不同的问题。

### 4.3 相关工作及各自的额外信息需求（简述）

| 工作 | 主要决策层 | 依赖的额外信息 | 与本项目的关系 |
| --- | --- | --- | --- |
| Continuum | TTL / 保留 + 程序级调度 | 服务端请求间隔历史、程序身份 | A0 的项目侧来源；非源码级复现 |
| SAGA | 调度 + TTL + WA-LRU 驱逐 | Agent Execution Graph（AEG）或 trace 推断 | 机制参照；需要工作流图，本项目不接入 |
| KVFlow | KV-node 驱逐 + 预取 | Agent Step Graph、steps-to-execution | 信号族对照；依赖工作流结构 |
| CacheWise | 前缀感知调度 + 预测式驱逐 | 工具调用元数据（类型/参数） | 信号族对照；预测器需离线训练 |
| WFEF | 驱逐算法评估 | 无外部工作流信息 | 反向证据来源；LRU 稳健但有容量反例 |

【事实】各论文的实验条件、版本与不可移植结论见 [`References&Notes/论文总结.md`](References&Notes/论文总结.md) 与 [`References&Notes/对比笔记.md`](References&Notes/对比笔记.md)。本文只引用其机制与证据边界，不把论文结果当作本项目预期。

【解释】这些工作说明"前缀复用 + 多轮工作流"确实带来额外结构，但也说明它们各自依赖不同的外部信息（AEG、ASG、工具元数据）。本项目的约束是**优先使用本地运行时信号**；是否能在这个约束下获得可测量的改进，是待检验问题，而不是已成立的新颖性主张。

## 5. 必须区分两个决策层

### 5.1 Entry 级 unpin / pressure release

【事实】在 Continuum 风格机制中，受保护的最小逻辑单位是 **Entry**，以 `(program_id, prefix_id)` 为键；一个 Entry 关联一组 Block。**解除保护（unpin）**把某个 Entry 的 `protected` 状态置为假，使其关联 Block **获得被回收的资格（eligibility）**。

【事实】这是**逻辑层操作**：它不移动任何数据、不释放任何显存。压力释放循环的终止条件是"获得资格的 Block 数达到容量目标"，而**不是**"这些 Block 已经被移除"。当前实现中保护是 Entry 级布尔量，`block_ids` 是观测到的关联块列表，不是保护范围。

### 5.2 Block 级 physical eviction

【事实】**受害者选择（victim selection）**在已获得资格的候选 Block 中，决定最终移除哪些物理块。**驱逐（eviction）**是真正把物理 Block 从 GPU 缓存中移除的操作。`ref_cnt > 0` 的块不得被驱逐，这是所有策略（含基线）必须遵守的硬约束。

### 5.3 为什么两者不能互相替代

【解释】以下四个命题不能互相推出：

1. **改变 Entry 释放顺序，不自动证明物理 victim 选择有收益。** 释放顺序改变的是"哪些 Block 先获得资格"；最终移除哪些 Block 仍由下游 selector 决定。若 selector 在两种顺序下选出同一个 victim 集合，则顺序改变没有改变"真正重要的决定"。
2. **释放更多 Block，不自动等于驱逐更多 Block。** 已暴露但未被选中的 Block 仍留在缓存中，只是未来暴露于驱逐风险。把"新获得资格"当作"已被驱逐"会高估一次释放的代价。
3. **驱逐更多 Block，不自动等于更多重算。** 被驱逐的块可能从未被再次请求，或已被其他副本/共享前缀覆盖；是否产生重算取决于后续请求与内容身份。
4. **逻辑 Entry 边界不等于物理 Block 所有权边界。** 一个物理 Block 可被多个逻辑前缀链共享；释放某个 Entry 的保护，不能在该 Block 仍被其他受保护 Entry 持有时就把它变成可回收。

### 5.4 证据层级：物理驱逐、APC miss 与请求级重算是不同的观测

【事实】Phase 3 的 v3 协议把证据分为四层，禁止互相冒充（v4 延续主指标与 `N/E/C` 独立定义；v3 保留为历史协议）：

| 层 | 含义 | 能支持的主张 |
| --- | --- | --- |
| **L1 预测受害者** | 由冻结 eligibility + native rank 推算的候选集合 | 可判别性分析；**不是**物理事实 |
| **L2 物理逐出** | `BLOCK_EVICTED` / `VLLM_NATIVE_HASHED_CACHE_ENTRY_EVICTED` 事件 | "发生过逐出"、机制暴露量 |
| **L3 内容身份** | 逐出内容键与后续请求前缀内容键是否一致 | **内容级时间关联**；**不是**完整物理因果归属 |
| **L4 重算后果** | 请求级 `E`、`C`，即 `Σ(E − C)` | **主指标；唯一的效果依据** |

【事实】与 L2–L4 并列，逻辑释放/资格是更早的一个观测层：它只说明"某块可以成为候选"，既不说明被逐出，也不说明被重算。`ownership_level_attribution = NOT_ESTABLISHED`：即便内容键在逐出事件与后续请求前缀中先后出现，也只能支持"内容级时间关联"，不能证明"该块是被本策略而不是被自然淘汰或别的请求杀掉的"。见 v3 §4.1、§4.3（历史协议中的证据分层定义）与 [Protocol v4 §1](https://github.com/zhengjiahong-ai/LLM-KV-Cache-Optimization/blob/main/docs/phase3-final-evaluation-protocol-v4.md)。

【事实】`N`、`E`、`C` 的口径是：`N` = 原生 prompt tokens；`E` = 按冻结 eligibility 定义可复用的前缀 tokens；`C` = Native APC 实际命中 tokens；强制 `0 ≤ C ≤ E ≤ N`，并满足恒等式 `Σ(N − C) = Σ(E − C) + Σ(N − E)`。`E` 必须与臂无关：同一 cell 的六个臂逐请求 `E` 必须相同。见 [Protocol v4 §1](https://github.com/zhengjiahong-ai/LLM-KV-Cache-Optimization/blob/main/docs/phase3-final-evaluation-protocol-v4.md) 与 [`docs/research-status.md`](../research-status.md) 的测量规则。

### 5.5 术语纪律

【事实】按 [`专业术语表.md`](专业术语表.md) §1：

> **unpin 改资格，victim selection 选对象，eviction 才移除。** 三者不可互换，也不互相蕴含。

因此本文不使用"释放"来指代"驱逐"，不使用"eligible"来指代"selected"，也不把"pressure release 达标"写成"缓存已回收"。

## 6. 本项目已经实现的机制

### 6.1 Phase 1A：Block 级驱逐适配器

【事实】Phase 1A（`CLOSED`）验证了真实 GPU 推理中的 `EvictionPolicyAdapter` 路径：从 vLLM cached free blocks 经 `VLLMEvictionBridge` 构造 `EvictionCandidate`，由策略返回 victim block IDs，再交给原生 `BlockPool` 记账与清理。该路径在真实运行时复现了原生 LRU victim 顺序，并保留原生块表、哈希与引用计数记账。见 [`docs/research-status.md`](../research-status.md) 与 [`docs/policy-adapter-design.md`](../policy-adapter-design.md)。

【解释】Phase 1A 证明的是"接口可工作、记账未被破坏"，不是"某个策略有性能收益"。

### 6.2 Phase 1B：Continuum 风格项目基线

【事实】Phase 1B（`CLOSED`）集成了项目侧的 Continuum 风格基线，并通过真实运行时验证：显式 program/session 身份、在线工具间隔/复用历史、动态 TTL 估计、独立软保护状态、惰性 TTL 过期、确定性压力释放、窄范围 program-level 准入顺序，以及 Phase 1A 驱逐适配器与原生 BlockPool 清理。见 [`docs/experiments/phase1b-continuum/final-report.md`](../experiments/phase1b-continuum/final-report.md)。

【事实】该实现**不是**对 Continuum 论文完整系统的源码级复现，也**不得**表述为"复现/优于 Continuum 论文"。它是适配到 vLLM 0.27.1 的项目基线。见 [`docs/baseline-freeze.md`](../baseline-freeze.md)。

### 6.3 A0 / A1 / A2 三个实验臂（按决策层区分）

【事实】当前已评估的实验臂按决策层定义如下：

| 臂 | Entry forced release | Physical block victim selection |
| --- | --- | --- |
| **A0** | 冻结的 Continuum 风格确定性基线：`(deadline, min native rank, identity)` | 现有 eligibility 下的 native LRU |
| **A1** | cost-aware Entry 级选择（`single_step` / `per_unit` / `pair_lookahead` / `deadline_fallback`） | 与 A0 相同的 Block 层基线 |
| **A2** | A0 的 Entry 级释放 | cost-aware Block 级 selector |

【事实】`A2` **不是** A1 + A2 的联合策略；A1 与 A0 的差异不能单独建立 A1 的 q/λ/pair-lookahead 信号的独立价值。`Sufficient-first + earliest-deadline` 是任何未来正式结论都必须包含的强比较对象。见 [`docs/research-status.md`](../research-status.md)。

【事实】A1 有可工作的 Entry 级成本感知原型；A2 有可工作的运行时 Block 适配器，并在身份或适配器契约证据不足时**fail-closed 回退到 Native LRU**。这两点说明"组件存在"，**不**说明独立性能收益已成立（§7）。

### 6.4 Phase 3 Stage 1 / Stage 2 工程

【事实】Phase 3 的两项工程已合并到 `main`：

- **Stage 1（PR #93）**：六臂 cell materializer，把同一冻结 base cell 展开为 N0/A0/A1/A2/A3/E0，保持 trace、Explicit Token IDs、pressure inputs 与 replay boundaries 一致；同时完成 E0 与 N0 的 CPU/Mock 集成。它是 **cell expander**，不是 cohort 构建器。
- **Stage 2（PR #94）**：独立的 N/E/C 离线 evaluator，`E` 由冻结请求集合与冻结 eligibility 独立重建，不以 `C` 回退；跨臂校验逐请求 `N`/`E` 相等；任何证据缺失或身份不一致按 `FAIL_CLOSED` 处理。

见 [Stage 1 closeout](https://github.com/zhengjiahong-ai/LLM-KV-Cache-Optimization/blob/main/docs/experiments/phase3-engineering-preparation-stage1.md)、[Stage 2 closeout](https://github.com/zhengjiahong-ai/LLM-KV-Cache-Optimization/blob/main/docs/experiments/phase3-engineering-preparation-stage2.md) 与 [canonical status](../research-status.md)。

【解释】Stage 1/2 的完成是**工程与测量基础设施**的完成，不是性能假设的验证。CPU/Mock 通过只说明映射、隔离与评估器逻辑正确，不说明任何策略在真实 vLLM 上更好。

### 7.2 A1：选择级证据与有界 Native 证据

【事实】**选择级**：Gate 2 的事后决策分析发现，`Sufficient-first + earliest-deadline` 复现了全部 **54/54** 个被记录的 A1 Gate 2 forced-release 选择；A1 自身排序是 `(expected_recompute, deadline, identity)`，因此在该语料上"分数项"不是复现所必需的。canonical ledger 的结论是：A1 的**独立 cost-model 信号未被证明**。见 [`docs/experiments/phase2g-a1/README.md`](../experiments/phase2g-a1/README.md) 与 [`docs/research-status.md`](../research-status.md)。

【事实】更早的 A1 Native Gate 2 曾报告 **12 BETTER / 1 WORSE / 22 TIED / 1 INCONCLUSIVE**；但 Gate 2 review 证明该结果使用的 `recomputed_tokens` 实际是 `N−C`（actual prefill），冻结的 `E−C` 从未被计算，且原始证据在本机不可复算。因此这组数字只按 M6 的报告保留，**不得**作为 A1 重算收益证据。见 [`phase2g-gate2-review/README.md`](../experiments/phase2g-gate2-review/README.md)。

【事实】**有界 Native**：PR #82 的 54-run 评估（Qwen2.5-Coder-1.5B-Instruct、单张 RTX 4090D、9 个冻结 group）报告 A1 **0 better / 1 worse / 8 tied**（重算 token，better/worse/tied），未观察到 A1 的重算收益。该评估是**单次重复的探索性**证据，内容级因果归因 `NOT_ESTABLISHED`。见 [`bounded results`](https://github.com/zhengjiahong-ai/LLM-KV-Cache-Optimization/blob/main/docs/continuum-native-cost-aware-bounded-results.md) 与 [`docs/research-status.md`](../research-status.md)。

【事实】该报告同时记录：A1 共产生 **29** 次 release-selection 步骤，其中 **27** 次与 `Sufficient-first + Earliest Deadline` 一致、**25** 次与 `Sufficient-first + Minimum Overshoot` 一致；`q` 在 **18/29** 步非恒定；A1 的 release 序列只在 **2/18** 个 pressure cell 与 A0 不同（均在 `g05-low-high`），且只有 moderate cell 随后出现非零 token delta（**+3,712**，方向为 worse）。这些是**选择层差异**，不是重算收益；报告明确将其与"未观察到 token benefit"分开记录。

【解释】"54/54"与"54-run"是两件不同的事：前者是**选择复现数**，后者是**成功 Native 运行数**。二者不可混写。

【解释】因此，canonical ledger 中 "Native evidence of some beneficial entry-release differences" 只能按**选择层差异**理解；它不能与 PR #82 的 "no observed recomputation-token benefit" 合并成单一结论。前者说明 A1 的释放序列确实与基线不同，后者说明这些差异在该有界评估中**没有转化为重算 token 收益**。

### 7.3 A2：有界评估与 INCONCLUSIVE

【事实】Phase 2G A2 有界评估的冻结结论是 **0 better / 3 worse / 33 tied**（36 draws），研究判断为 **`INCONCLUSIVE`**：它既不是 A2 与 LRU 普遍等价的证明，也不是正式收益证据。见 [`docs/experiments/phase2g-a2-bounded-value-evaluation.md`](../experiments/phase2g-a2-bounded-value-evaluation.md) 与 [`docs/experiments/phase2g-a2-research-judgment.md`](../experiments/phase2g-a2-research-judgment.md)。

【事实】该评估的内容验证与物理归因限制必须一并记录：

- **402 / 778（约 51.7%）** 的 A2 block 决策以 `content_unverified` 回退；
- **122** 个强制释放窗口中，**82** 个无法配对或身份不完整；
- Gate 2 v3 的 **72/72** 个选择对为 `SELECTION_NOT_OBSERVABLE`，零 token 差异**不能**证明决策相同。

【解释】这意味着该战役在很大程度上"未能检验算法"，而不只是"检验后未发现差异"。因此不能把它读成"A2 无效"的普遍结论；同样，也不能把少数较好的 cell 读成"有效"的证据。

### 7.4 W1-B：描述性 smoke，不是总体收益

【事实】W1-B（M1 验收，合并为 `fc9626da`，2026-10-23）报告 4 组 × A0/A1/A2 = **12 次成功运行**，每臂每组一次重复。分组 A1−A0 重算 token 差为 **−1056 / 0 / −1616 / −1232**（描述性总和 **−3904**）；**A2−A0 每组为零**，且未观察到 A2 与 Native-LRU 的 victim 集合分歧。见 [PR #73](https://github.com/zhengjiahong-ai/LLM-KV-Cache-Optimization/pull/73) 与 [`docs/research-status.md`](../research-status.md)。

【事实】M1 验收明确**不**建立：总体收益、对 `Sufficient-first` 的优越性、单次物理驱逐的因果、对 Continuum 论文原始 serving 负载的复现。RC3 只标注**时间关联**，内容级因果归因为 **`NOT_ESTABLISHED`**。

【解释】−3904 是一个 4 组的描述性总和，不是效应量估计；A2−A0 全零也不能读成"A2 等价于 LRU"，因为该 smoke 中未观测到 victim 集合分歧，决策暴露不足。

### 7.5 不得过度解读

- 【解释】**负结果不是普遍否证。** A2 的 0/3/33 与 PR #82 的 0/1/8、0/3/6 都受内容验证率、决策暴露与单次重复限制；它们不支持"A2 在所有负载上无效"。
- 【解释】**部分正结果不是已证明的改进。** W1-B 的 −3904 是描述性关联；A1 的 54/54 是"简单规则可复现"，不是"成本模型有价值"。
- 【解释】**不同实验不可合并。** Phase 2E、Phase 2G、PR #82、W1-B 使用不同数据集/协议/证据标准；把它们拼成一个"总体结论"会掩盖缺失与偏差。

## 8. 为什么严格的真实 vLLM 评估是当前优先事项

【解释】当前优先做评估，不是因为"策略空间已经穷尽"，而是因为**没有可靠的测量与归因，任何策略结论——无论正负——都不可解释**。具体有八个必须闭合的测量问题。

### 8.1 八个必须闭合的问题

1. **不同的 victim 顺序不一定降低重算。**
   顺序只有在改变最终被移除的 Block 集合时才可能产生效果；即使 victim 集合不同，被驱逐的块也可能从未被再次请求，或重算代价相同。必须把"顺序变化 → victim 集合变化 → 重算变化"逐层测出来，而不是从顺序差异直接推断收益。

2. **逻辑 unpin 不是物理驱逐。**
   压力释放只改变 eligibility；释放循环在"资格数达标"时停止，而不是在"块被移除"时停止。把新获得资格当作已驱逐，会同时高估释放的代价与收益。

3. **物理驱逐必须连到后续 APC miss 与请求级重算。**
   L2 事件只说明"某块被移除"；要证明效果，必须把逐出内容与后续请求前缀做内容级关联（L3），并以请求级 `Σ(E − C)`（L4）作为唯一效果依据。仅凭 L2 事件数不能主张性能。

4. **内容身份与共享前缀证据必须可信。**
   内容哈希链必须完整、`ref_cnt` 必须为 0、共享块必须被正确归属。A2 的 402/778 `content_unverified` 说明身份不确定性已经足以让大部分决策落在回退路径上。若身份证据不可信，复杂打分只会制造虚假信心。

5. **候选集合与请求输入必须跨臂可比。**
   同一 cell 的六个臂必须共享逐字节相同的 replay plan、Explicit Token IDs、到达偏移、并发、KV 容量、block size 与 chunked-prefill 预算；唯一允许的差异是 policy 字段。否则臂间差异会混入输入差异。

6. **`N/E/C` 必须独立且一致地导出。**
   `E` 只能来自冻结请求集合与冻结 eligibility，不能由 `C` 回退、下界或修补；同一 cell 的逐请求 `E` 必须跨臂相同。恒等式 `Σ(N−C) = Σ(E−C) + Σ(N−E)` 必须成立。若 `E` 随臂变化，`Σ(E−C)` 就不再是同一把尺子。

7. **统计推断必须使用正确的独立单元。**
   独立单元是 **Workload Group**，不是 run、turn 或 request。两个 load 档属于同一 group，不得合并成 40 个独立样本；每个 load 档的 `n = 20`。Phase 3 的定位是**探索性效应量估计**，不是确认性显著性检验；repeat 不增加独立样本量。

8. **完成的软件组件或 CPU/Mock 测试不构成性能假设。**
   A1/A2 的适配器可以工作、Stage 1 的六臂 materializer 可以展开 cell、Stage 2 的 evaluator 可以通过测试；这些只证明工程正确性与可测量性。性能假设仍需真实 vLLM 上的配对、可归因证据。

### 8.2 为什么必须先提高保真度与归因

【解释】如果上述条件不成立，可能出现两种同样糟糕的结果：

- **"全零不可解释"**：基线重算量本身接近 0，或所有候选的代价排序恒同，此时 `Δ = 0` 既不支持也不否证任何算法。Phase 2E/2G 已经出现过这种情形（moderate 档实测重算比例约 0.65%）。
- **"差异不可归因"**：观测到 `Δ ≠ 0`，但无法判断它来自成本模型、阶梯结构、回退分支、输入差异还是测量噪声。此时把差异写成"算法有效"是过度归因。

【解释】因此，**改进实验保真度与归因是扩展策略空间的前提，而不是它的替代品**。这也是 Phase 3 先设 Headroom（开跑前冻结）、G3-CM 可判别性、S2A/S2B/S2C 分支统计与四层证据的原因：它们的作用是让"有没有差异"和"差异能否解释"成为可判定的问题。

## 9. 冻结的 Phase 3 六臂评估要建立什么

> **状态（截至 2026-11-07 的 `main`）**：Phase 3 的最终协议是 **Protocol v4（Option F）**。M1 于 2026-11-06 接受 Option F（Issue #98 / PR #97），Protocol v4 作为独立文档生效；**Protocol v3 保留为不可变历史协议**。Stage 1（PR #93）与 Stage 2（PR #94）工程已合并；Option F 的工程适配经 PR #99 合并（`a7fe138`）。**G0 已于 2026-11-07 验收**：既有 **40-run A0 负载标定被复用（不重跑）**，**30-run A0 Noise Calibration 已获 M1 授权**（执行方 M6），**240-run 六臂 Main Campaign 仍锁定/未授权**。可变状态以 [`docs/research-status.md`](../research-status.md) 与 [`phase3-option-f-engineering-status.md`](https://github.com/zhengjiahong-ai/LLM-KV-Cache-Optimization/blob/main/docs/experiments/phase3-option-f-engineering-status.md) 为准；本文不复述其状态表。

### 9.1 六个实验臂

【事实】Phase 3 的六臂设计为 **N0 / A0 / A1 / A2 / A3 / E0**。下表只说明各臂在两层决策中的位置与对照目的，算法语义以冻结协议为准：

| 臂 | Entry release | Block victim | 对照目的 |
| --- | --- | --- | --- |
| **N0** | 无 forced release（保留压力请求、`boundary_id`、逻辑时间线与 Pressure Barrier，仅禁用项目侧强制 Entry Release） | native LRU + APC | 绝对基线；与 A0 一起检验"强制释放本身是否有净收益"（H3） |
| **A0** | 冻结 `(deadline, min native rank, identity)`，无阶梯 | native LRU | 项目侧 Continuum 风格 Entry Release 基线 |
| **A1** | 冻结 cost-aware Entry 阶梯（Step 2 = `q·[λN+(1−λ)min(need,N)]`） | native LRU | Phase 2G 冻结的 Entry 层算法 |
| **A2** | 同 A0 | cost-aware Block selector | Phase 2G-A2 冻结的 Block 层算法 |
| **A3** | 冻结阶梯，Step 2 = `(L, deadline, identity)`，`L = q·prefill·S/m` | native LRU | Phase 2I 冻结算法；检验完整 A3 vs A0（H1） |
| **E0** | 同 A1 阶梯，Step 2 = `(deadline, identity)` | native LRU | 最简强对照；`A3 − E0` 隔离成本模型（H2） |

【事实】Protocol v4 固定两个工作点：**C1 = 256 `required_blocks`**、**C2 = 1024 `required_blocks`**（2048-block KV pool 不变）。C1/C2 是条件名称，不得改称 low/high pressure；20 groups × 2 conditions × 6 arms = 240 个主战役 cell/run。既有 A0 标定给出 C1 18/20、C2 20/20、合计 **38/40** 个 Headroom-qualified cell，配对主分析使用 **18 个完整 group**。

【解释】A3 与 E0 是 Phase 3 新增的臂，不属于历史 A0/A1/A2 评估；N0 是绝对基线，不是"最优策略"。A2 仍然只改 Block 层，不能与 A1/A3 的 Entry 层改动混为一谈。

### 9.2 三个可证伪假设

【事实】协议把假设拆成三个独立问题：

- **H1 EFFICACY**：`A3` 的 `Σ(E−C)` 低于 `A0`；证伪条件是配对 CI 含 0 或方向为正。
- **H2 VALUE**：成本模型 `q·prefill·S/m` 优于不使用成本模型的最简阶梯 `E0`；证伪条件是 `A3 − E0` 的 CI 含 0，或在可判别决策不足时判 `NOT_EVALUABLE`。
- **H3-0 CONSTRAINT**：强制释放本身（`A0`）相对 `N0` 在全部 Headroom-qualified cells 上有净收益；证伪条件是 `A0 − N0` 的 CI 含 0。
- **H3-R**：同一对比在 RESPONSIVE 子组（9 groups / 16 qualified cells）上的独立假设，**不替代 H3-0**；两者分别报告。

【解释】H2 是最容易被忽略、但对项目结论最关键的一项：如果 `A3 ≈ E0`，则成本建模在本负载上没有产生可测量的独立价值，必须如实报告；但若可判别决策不足，应判 `NOT_EVALUABLE`，**不能**写成"成本模型无价值"。

### 9.3 主指标与证据分层

【事实】主指标是绝对 token 数 `Σ(E − C)`；`recompute_ratio` 与 `apc_reuse_ratio` 只作补充，不得替代主指标。`E` 必须与臂无关；`0 ≤ C ≤ E ≤ N`；恒等式 `Σ(N−C) = Σ(E−C) + Σ(N−E)` 必须成立。证据按 §5.4 的 L1–L4 分层；L4 是唯一效果依据，`ownership_level_attribution = NOT_ESTABLISHED`。

## 10. 仍属于潜在未来工作的研究方向

【事实】Member 2 早前提出的四个优化方向——Block Idea 1（证据感知介入门槛与 Native-LRU 回退）、Block Idea 2（工作流/运行时信号用于 Block victim selection）、Entry Idea 3（下游代价感知的 Entry 释放顺序）、Entry Idea 4（partial-tail Entry unpinning）——是**潜在未来研究方向**，不是当前实验臂，也不属于冻结的 Phase 3 六臂战役。

【事实】四个方向**未全部实现**，其独立性能收益**未建立**，部分方向甚至存在表示层面的可实现性风险（例如 partial-tail unpin 需要 sub-Entry 保护表示与共享所有权正确性）。完整论证、状态矩阵与未来评估条件见 [`kv_cache_optimization_motivation_and_design_proposal.md`](kv_cache_optimization_motivation_and_design_proposal.md)；本文不复述其算法细节。

【解释】保留这四个方向的意义在于：它们把"Entry 释放顺序/粒度"与"Block 受害者选择"中的开放问题明确记录为可证伪的研究问题；但它们不能作为当前项目已取得的成果，也不能替代 Phase 3 对既有实验臂的严格评估。

## 11. 范围边界

- 不改注意力内核；不做多卡与分布式；不做 CPU KV offloading；不复现 PagedAttention / vLLM 本身。
- 不复现 ARC、RLT/LBGR、SAGA、KVFlow、CacheWise 的完整系统；它们只作为机制对照与证据来源。
- Continuum 风格基线复现其动态 TTL / retention 与程序级调度决策逻辑，**不复现其完整系统**，也不声称与论文逐行等价。
- 不在本项目中预设"复杂策略优于 LRU"；任何策略结论必须来自可归因的 Native 证据。
- 完整排除清单见 [`docs/baseline-freeze.md`](../baseline-freeze.md) 的 Explicit First-Version Exclusions。

## 12. 小结

【事实】本项目研究的是 **vLLM 0.27.1 + GPU APC 上的 KV 缓存保留与驱逐**。Entry 级 unpin / pressure release 与 Block 级 physical eviction 是两个不同的决策层；A1 改动 Entry 层，A2 改动 Block 层，A0 是两者共同的对照基线；Phase 3 进一步用 N0/A0/A1/A2/A3/E0 六臂把"强制释放本身""完整策略""成本模型"拆成可分别检验的问题。

【事实】项目已经完成真实运行时适配器验证、Continuum 风格项目基线、A1/A2 原型与有界 Native 评估，以及 Phase 3 Stage 1/2 的六臂 materializer 与独立 N/E/C evaluator。但 A1 的独立成本模型价值未证明，A2 的研究判断为 `INCONCLUSIVE`，W1-B 只是描述性 smoke。

【解释】因此，当前的研究动机不是"证明某个更复杂的策略更好"，而是**先建立可信的测量与归因**：让逻辑释放、物理驱逐、APC 命中与请求级重算各归其位，让候选集合与 `N/E/C` 跨臂可比，让统计单元与门槛在开跑前冻结。只有在这个基础上，Phase 3 的六臂比较才能回答"成本感知驱逐是否在可测量的重算代价上优于 Native LRU / 冻结基线 / 最简强对照"。

【假设】四个未来方向是否值得继续，取决于它们能否在未来的授权评估中通过同样的证据标准；在此之前，它们保持 proposal / hypothesis 定位。
