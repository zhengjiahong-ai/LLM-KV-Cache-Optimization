## 1. 提出问题：KV 缓存的内存瓶颈与驱逐决策

### 1.1 KV 缓存是什么，为什么会成为瓶颈

大语言模型（LLM）生成文本是自回归的：每生成一个 token，都需要用到之前所有 token 的注意力信息。为避免重复计算，推理系统会把已算出的 Key/Value 张量缓存下来，这就是 **KV 缓存（KV Cache）**。它的代价是显存占用随上下文长度和并发请求数近似线性增长；在多轮对话、长文本和智能体（Agent）场景下，单个会话的缓存可以达到数 GB 量级（SAGA 论文报告其考察的 Agent 任务 KV 缓存为 2–12 GB）。

GPU 显存有限。当缓存总量接近显存上限时，系统可以延后新请求、将缓存换出到 CPU 内存，或**驱逐（eviction）**部分缓存。被驱逐的缓存再次被需要时，系统可能需要重新执行**预填充（prefill）**，即重新计算这段历史。长上下文的预填充通常是计算密集阶段，因此会带来延迟惩罚。

一个量化背景：PagedAttention 论文指出，传统连续分配方式下 KV 缓存的内存利用率可低至 20.4%。分页机制将缓存切成固定大小的块管理，改善了存放和回收方式；但论文没有提出按候选块重算损失排序的策略。

### 1.2 关键痛点：块的重算代价是高度异构的

驱逐决策的核心矛盾在于：**不同缓存块被逐出后的损失差别巨大**，这就是本文所说的"成本异构性"。举例说明：

- 一段被大量请求共享的系统提示词（system prompt）前缀可能很长。若它被逐出，后续请求重新使用该前缀时需要较多预填充计算；
- 一段较短的对话尾部即使再次被用到，所需补算通常较少。

只使用新近度的策略无法直接表示上述差别。在重算代价差异较大的负载中，它可能逐出较长、较可能复用的前缀，导致更多补算。补算会影响首词延迟（TTFT，Time To First Token）和吞吐。

这个问题在两类现代负载下尤其突出：

- **多轮对话与长上下文**：会话越长，前缀越贵，误逐一次的损失越大；
- **Agent 工具调用**：模型调用外部工具后会暂停推理，缓存短时间内可能没有访问。SAGA 论文在 SWE-bench 上报告，vLLM v0.6.0 有 38% 的执行时间用于在 Agent 步骤间重建 KV 缓存。

由此得到本项目的核心问题：

> 当 KV 缓存容量不足时，应依据什么信号选择被逐出的块，才能在释放足够空间的同时，尽量不逐出"重算昂贵且可能被复用"的块？

## 2. 现有工作与本项目的差别

围绕上述问题，已有工作可以分为三类。这里只点明各自与本项目目标（在线动态感知异构重算成本）之间的差距，机制细节见 `论文总结.md`。

### 2.1 逐出类策略：主要利用访问历史或随机性

- **LRU / Leaf-LRU**：LRU 按最后访问时间逐出；Leaf-LRU 在前缀树中优先从叶子 token 选择。RLT 论文在其前缀共享模型下证明 Leaf-LRU 的最坏竞争比可为 \(O(n)\)。这类策略不直接估计候选块的重算时间。
- **ARC（Recency-Frequency Adaptive）**：在新近度之外引入频率信号，并通过幽灵缓存反馈调整两类队列的空间配比。它主要估计复用模式，而非逐出后需要补算多少。
- **RLT（Randomized Leaf Token Eviction）**：在未标记的叶子 token 中随机逐出，以减弱对到达顺序的依赖。随机选择本身不估计单个候选的重算成本。

三者均未以候选块的预计重算时间作为直接的排序信号。

### 2.2 保留与工作流感知策略

- **Continuum（TTL）**：用工具调用历史、缓存占用和排队影响计算 TTL，并在 TTL 内 pin 请求的 KV 缓存。TTL 到期后解除 pin；内存不足时会选择部分已 pin 请求解除保护。它的重点是决定保留时长，而不是对所有候选块逐一排序。
- **SAGA（WA-LRU + TTL）**：用工具类型延迟分位数设置 TTL，并按显存压力缩短 TTL。其 WA-LRU 根据 AEG 预测的未来复用概率、新近度和缓存大小排序候选。AEG 可由框架提示提供，也可由历史 trace 推断，因此需要额外的工作流信息或推断模块；排序分数不直接表示候选块的重算时间。

Continuum 的核心是保留时长，SAGA 还包括工作流感知的逐出排序。本项目拟在容量不足时，根据运行时观察到的成本和复用信号排序候选块；它与 TTL 可组合。

### 2.3 小结

| 策略类别 | 代表工作 | 决策信号 | 与本项目目标的差距 |
| --- | --- | --- | --- |
| 逐出类 | LRU、ARC、RLT | 时间戳 / 频率 / 随机 | 不直接估计候选块的重算时间 |
| 保留与工作流感知类 | Continuum、SAGA | 工具统计 / AEG / 调度状态 | 关注保留窗口或工作流预测，信息需求更高 |

在本文比较的工作中，尚未发现同时满足以下条件的方法：在逐出时刻，只依赖本地运行时可观测信号，并直接估计每个候选块的重算损失。

## 3. 抛出优化机会：成本感知的在线驱逐策略

### 3.1 核心想法

本项目拟设计一种 **cost-aware KV-cache eviction policy**：在缓存容量不足、必须逐出时，对每个候选块在线估计其驱逐损失，优先逐出损失最小的块。驱逐损失的概念形式为：

```
驱逐损失 ≈ 重算成本 × 复用概率 ×（内存足迹、当前缓存压力的修正）
```

各信号的取值方式保持务实，均为运行时可观测的量：

- **重算成本**：以该块对应的缓存长度/块数为主要代理量，不追求精确的 FLOPs 建模（长块重算更贵这一关系已足够用于排序）；
- **复用概率**：来自在线维护的近期复用历史，不需要任何先验的工作流信息；
- **内存足迹与缓存压力**：作为修正项，使决策响应当前的全局显存状态。

需要强调两点边界：

1. **具体的评分函数尚未冻结**。按 `docs/experiment-plan.md` 的安排，评分形式将在基线实现与 profiling 之后确定，且各信号分量可配置，以支持消融实验（验证收益确实来自成本信号本身）。
2. **目标是明确的，结果是待验证的**。我们预期该策略能在重算代价异构的负载上减少高价值块的误逐，从而降低 TTFT、减少重算 token 总量；但在请求代价相近的负载上，它可能退化为与简单策略相当、并额外付出决策开销。这正是实验计划中负载敏感性分析（RQ3）要回答的问题。

### 3.2 与 Continuum TTL 的关系：正交且可组合

本项目的策略与 Continuum 的 TTL 回答的是不同的问题：

| | Continuum TTL | 本项目 |
| --- | --- | --- |
| 决策点 | 请求挂起时：保留多久 | 容量不足时：逐出谁 |
| 决策对象 | 租约时长 | 候选块排序 |
| 信息需求 | 工具调用历史和系统状态 | 本地运行时信号 |

两者并不冲突：TTL 决定"哪些缓存暂时不参与竞争"，成本感知驱逐决定"必须腾出空间时先牺牲谁"。理论上两者可以叠加使用；在课程项目范围内，我们可尝试组合实现，或将 Continuum 风格 TTL 作为强基线（Baseline 2）进行同口径对比，以回答"成本感知驱逐相对保留类策略能带来多少额外收益"（RQ2）。

### 3.3 对应到项目的研究问题

上述动机直接对应实验计划中已冻结的三个研究问题：

- **RQ1**：成本感知驱逐是否优于基于新近度的 LRU（Baseline 1）；
- **RQ2**：成本感知驱逐相对 Continuum 风格 TTL 基线（Baseline 2）表现如何；
- **RQ3**：在何种负载条件下收益最大（长短请求比例、缓存压力、前缀复用程度）。

### 3.4 范围边界（不做什么）

为保持项目可行性，明确排除以下内容：不改注意力内核、不做多卡与分布式、不复现 ARC / RLT / SAGA 的完整系统、不训练模型；Continuum 基线只复现其 TTL / retention 决策逻辑。完整范围见 `docs/experiment-plan.md` 的 Scope Boundaries。
