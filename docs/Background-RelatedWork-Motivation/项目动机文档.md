## 1. 提出问题：从"驱逐谁"到"两层决策"

### 1.1 KV 缓存与预填充重算

LLM 自回归生成每产出一个 token 都要用到此前全部 token 的注意力信息。推理系统把已算出的 Key/Value 张量缓存下来以避免重复计算，这就是 **KV 缓存（KV Cache）**；其显存占用随上下文长度与并发请求数近似线性增长。当缓存总量接近显存上限时，系统只能延后新请求、换出到 CPU，或**驱逐（eviction）**部分缓存。被驱逐的缓存再次被需要时必须重新执行计算密集的**预填充（prefill）**，直接推高首词延迟（TTFT）。

两个可用于论证动机的论文数据（均为**论文报告**，条件见括注，不是本项目实测）：

- PagedAttention 论文报告，传统连续分配方式下 KV 缓存的有效内存利用率可低至 **20.4%**；
- SAGA 论文在其 SWE-bench 实验中报告（32 张 A100、vLLM v0.6.0、10 次重复），Agent 有 **38% 的总时间**花在重新生成工具调用期间被丢弃的 KV 缓存上，GPU 显存利用率平均仅 42%。

这两组数字说明：分配方式与保留/驱逐决策都会造成可观浪费。本项目不改变分配机制（沿用 vLLM 0.27.1 的 GPU APC），研究的是保留与驱逐决策本身。

### 1.2 关键观察：容量不足时的决策分成两层

本项目关注两个**不同**的决策点，代码中也是两条独立路径：

| 决策层 | 决策内容 | 主要代码位置 | 输出 |
|---|---|---|---|
| **Entry 级 unpin / pressure release** | 内存压力下释放哪些 Entry 的保护，使其关联的部分或全部 Block 获得被回收的**资格** | `src/kvopt/continuum/pressure.py` | 新获得 eligibility 的 Block 集合 |
| **Block 级 physical eviction** | 在真正可驱逐的候选 Block 中，最终移除哪些物理块 | `src/kvopt/runtime/vllm/adapter.py`（路径契约）、`src/kvopt/costaware/a2_native.py`（A2 运行时入口） | victim block ID 序列 |

两层不是同一操作，也不能互相替代：

- **unpin 不等于驱逐。** 释放一个 Entry 的保护只改变 eligibility；该 Entry 暴露出的 Block 是否被立即移除，取决于 Block selector 选了谁。压力循环的终止条件是"获得资格的 Block 数达到容量目标"，而不是"这些 Block 都被移除"。
- **已暴露但未选中的 Block 仍留在缓存中**，并在未来暴露于驱逐风险。把"新获得资格"当作"已被驱逐"会高估一次释放的代价。
- **Entry 释放顺序改变下游候选集合。** 先释放哪个 Entry，决定了后续哪些 Block 进入可驱逐集合，从而影响 Block selector 的选择空间。
- **逻辑 Entry 边界不等于物理 Block 所有权边界。** 一个物理 Block 可被多个逻辑前缀链共享；释放某个 Entry 的保护，不能在该 Block 仍被其他受保护 Entry 持有时就把它变成可回收。

因此，单独优化其中一层，**不能**证明另一层有效；两层协同的价值需要显式实验，不能由单层结果外推。

### 1.3 为什么两层之间仍存在值得研究的问题

1. **资格与实际移除之间存在缺口。** 现有实现在 Entry 层计算"释放这个 Entry 会新暴露哪些 Block"，但排序依据是这些 Block 的 `native_lru_rank` 最小值，并没有估计下游 selector 实际会淘汰谁、代价多大。
2. **Block 层当前只看到 deadline。** TTL 估计器消费了工具类型、请求间隔样本、排队延迟、`eta`、预填充重算开销等中间信号，但把它们压缩成标量 `ttl_seconds`；到达 Block 驱逐决策点的只有 `deadline_timestamp`（详见 §4.2）。
3. **保护粒度是 Entry 级布尔值。** `RetentionEntrySnapshot` 只带一个 `protected` 布尔量与 `block_ids` 元组，无法只释放一个 Entry 的尾部而保留其浅层共享前缀。
4. **共享 Block 的所有权记账在运行时候选层。** `ref_cnt` 存在于 `EvictionCandidate` 上（由 vLLM 块快照经 `VLLMEvictionBridge` 填充）；仓库内的 `KVCacheManager` 没有引用计数语义，且 `free()` 一次释放某请求的全部 Block，不能作为共享语义的参照。

## 2. 基线：Continuum 风格的 A0，以及项目实现的边界

### 2.1 三个实验臂按决策层区分

按 [`docs/research-status.md`](../research-status.md) 的口径，实验臂必须按决策层区分：

| 臂 | Entry forced release | Physical block victim selection |
| --- | --- | --- |
| **A0** | 冻结的 Continuum 风格确定性基线 | 现有 eligibility 下的 native LRU |
| **A1** | cost-aware Entry 级选择 | 与 A0 相同的 Block 层基线 |
| **A2** | A0 的 Entry 级释放 | cost-aware Block 级 selector |

`A2` **不是** A1+A2 的联合策略。A1 与 A0 的差异本身不能建立 A1 的 q/λ/pair-lookahead 信号的独立价值。**`Sufficient-first + earliest-deadline`** 是任何未来正式结论都必须包含的强比较对象。

### 2.2 项目实现不是对 Continuum 论文的逐行复现

按 [`docs/baseline-freeze.md`](../baseline-freeze.md) 的表述：项目实现的是一个**适配到 vLLM 0.27.1 的 Continuum 风格系统基线**，因为 vLLM 缺少 Continuum 原生的程序/会话身份、pin API、工具间隔状态与程序级调度原语。该基线**不得被描述为源码级的精确复现**；复现范围聚焦决策逻辑（动态 TTL、软保护、惰性过期与压力释放、程序级准入顺序），不复现其完整系统。

TTL 估计依赖的若干输入在 vLLM 中并非原生可用，实现中每个输入都被分类为 `NATIVE` / `OBSERVED` / `EXTERNAL` / `APPROXIMATED` / `UNAVAILABLE`；工具事件是**外部 workload/orchestrator 输入**，不是从 vLLM 重建出来的信号。

### 2.3 冻结的释放顺序

`docs/baseline-freeze.md` §8 把压力下的回退释放顺序冻结为：

```text
earliest retention deadline first
    -> native LRU rank as tie-breaker
```

代码中对应 `src/kvopt/continuum/pressure.py` 的 `_release_sort_key()`，返回 `(entry.deadline_timestamp, native_key, key.sort_key)`，其中 `native_key` 是该 Entry 释放后**新获得资格的 Block** 中最小的 `native_lru_rank`。代码注释将其称为**冻结的 A0 顺序（the frozen A0 order）**，而非随手实现的启发式。

这一点对研究动机很重要：现有 A0 基线**已经消费了一个下游量**（一次释放会暴露出的 Block 的原生 LRU 秩）。任何"下游感知"的新排序都必须证明它优于这个并非纯 deadline 驱动的基线，而不是优于一个假想的更弱基线。

## 3. 当前证据及其解释

### 3.1 已实现并经过真实运行时验证

- Continuum 风格基线已集成并通过真实运行时验证（Phase 1B，`CLOSED`）；
- 项目侧 `EvictionPolicyAdapter` 已在真实 GPU 推理中复现原生 LRU victim 顺序，并保留原生下游记账（Phase 1A）；
- W1-B 有界 smoke 已 M1 验收并合入（`fc9626da`，2026-10-23），4 组 × A0/A1/A2 共 12 次成功运行。

### 3.2 已观察到的项目结果（仅在其实验范围内成立）

- **A1**：有界评估完成；此前的 Gate 2 决策分析发现 **54/54** 个 A1 选择可被简单的 `Sufficient-first + earliest-deadline` 启发式复现；独立的 cost-model 信号**未被证明**。
- **A2**：有界评估结论为 `INCONCLUSIVE`；冻结战役中 **0 better / 3 worse / 33 tied**（36 个 draws）。这既不证明 A2 与 LRU 普遍等价，也不构成正式收益证据。该战役中 778 个 A2 block 决策里有 **402 个（51.7%）** 以 `content_unverified` 回退；122 个强制释放窗口中 82 个无法配对或身份不完整。
- **W1-B**：仅为 `BOUNDED_SMOKE_ONLY`。A1−A0 的重算 token 差为描述性总和 −3904（分组 −1056 / 0 / −1616 / −1232）；**A2−A0 在每一组都为零**，且未观测到 A2 与 Native-LRU 的 victim 集合分歧。接受 W1-B **不**建立总体收益、不建立对 `Sufficient-first` 的优越性、不建立单次物理驱逐的因果、也不构成对 Continuum 论文原始 serving 负载的复现。

逻辑释放、物理 hashed 驱逐、后续 APC 命中与请求级重算是**不同层次的观测**；仅凭时间上的先后关系不能推断因果。任何缺失的证据都必须保留其缺失状态并 fail closed。

### 3.3 论文报告的反向证据

*When Fancy Eviction Fails*（arXiv:2609.28870v2）在超过 200 亿 token 的生产 trace 上评估 14 种驱逐算法，报告：简单 LRU 出乎意料地稳健，与复杂的传统策略表现相当（频率类算法往往更差）；原因是结构性的——前缀复用主要由活跃会话的稳定节奏主导，使 recency 成为异常强的预测因子。论文同时指出前缀缓存与传统负载的差异（单轮请求普遍、会话足迹极度倾斜、因注意力计算随 token 深度增长而导致的非均匀 miss cost），并给出三项设计原则：以 recency 为基线、加入 quick demotion 过滤一次性提示、compute-aware eviction 优先处理昂贵 miss、capacity-adaptive eviction granularity。

**这是论文作者的结论，不是本项目的实验结果。** 但它直接影响四个方向的设计：任何"更复杂=更好"的预设都必须让位于可检验的问题。

## 4. 四个研究方向

四个方向相互独立、可组合，但必须先分别理解各自的效果。每个方向的完整论述（算法草图、评估矩阵、失败判据）见 [`kv_cache_optimization_motivation_and_design_proposal.md`](kv_cache_optimization_motivation_and_design_proposal.md)，此处只作动机层面的概括。

### 4.1 Block Idea 1 — 介入门槛与 Native-LRU 回退

- **研究问题**：自定义 Block 驱逐策略在什么条件下值得介入，何时应回退到原生 LRU 决策？
- **已有机制**：`A2NativeBlockAdapter.select_victims()`（`a2_native.py:538`）在内容身份或复用权重不可验证时已回退到 native LRU；`A2BlockSelector.select()`（`a2_selector.py:327`）是离线路径，两者输入不同，结果不能互推。
- **假设（H1）**：仅当候选集合与 Block/前缀身份足够可验证、提出的 victim 集合与真实基线有实质差异、且离线评估预测的收益超过预先声明阈值时才介入。
- **所需信号**：已验证的内容身份、候选集合完备性、真实基线 victim 集合。
- **潜在收益**：避免在身份不确定时用复杂打分制造虚假信心。
- **风险**：门本身可能频繁介入却不改变 victim 集合；预测收益与实测收益不相关；回退开销吞掉收益。
- **验证方法**：原生 LRU 基线 / 常开 A2 / 仅用结构诊断的门控 A2 / 用已验证期望损失的门控 A2，四者对比；门必须在留出任务上选阈值。
- **当前证据**：402/778 决策以 `content_unverified` 回退，说明身份不确定性已高到可能使该方向大部分决策落在回退路径上。

### 4.2 Block Idea 2 — Continuum 中间信号用于 Block victim selection

- **研究问题**：在 TTL 最终期限之外，Continuum 已掌握的中间信号能否改善 Block victim selection？
- **已有机制**：`estimate_ttl()`（`ttl.py`）消费 `next_tool_type`、全局/按工具类型的请求间隔样本、排队延迟、`eta`、`prefill_reload_seconds`，输出标量 `ttl_seconds`。
- **信号可得性（关键区分）**：必须区分三个事实——信号在仓库中存在、被 TTL 估计器使用、真正到达 Block 驱逐决策点。目前**只有 `deadline_timestamp` 到达 Block 层**；运行时决策契约为 `EvictionCandidate`（`block_id`、`ref_cnt`、`has_block_hash`、`lru_rank`、`content_hash`）加 `EvictionContext`（`required_blocks`、`free_blocks`、`total_blocks`、`timestamp`），上述中间信号均不在其中。
- **`ExternalToolDurationHistory` 的实际状态**：该类在 `history.py:52` 定义、`runtime.py:89` 初始化、`runtime.py:332` 写入，但 `src/` 内没有任何代码读取 `global_samples()` 或 `samples_for_tool()`（仅 `tests/test_continuum_runtime_lifecycle.py` 断言其写入结果）。它是**只写不读**的数据。使用它之前必须先实现并测试一个消费者，不能把它描述为已被驱逐算法使用。
- **假设**：中间信号在 deadline 之外提供增量预测价值。
- **所需信号**：扩展后的决策期输入，以及信号在驱逐时刻的因果可得性证明。
- **潜在收益**：更精细地区分"何时可能被复用"与"逐出的代价有多大"。
- **风险**：TTL 已吸收部分信号导致重复计数；样本量不足以估计条件间隔分布；契约扩展破坏 adapter 的不可变性保证。
- **验证方法**：同一候选集合与容量目标下，deadline-only vs 逐个加入单一信号 vs 多信号模型；必须做 conditional on the deadline 的消融。
- **当前证据**：无。该方向尚未被检验。

### 4.3 Entry Idea 3 — Unpin 排序

- **研究问题**：现有 `_release_sort_key()` 的 Entry 释放顺序能否改进，尤其是考虑释放后新获得资格的 Block 与下游 selector 实际可能选择的 victim？
- **已有机制**：`_newly_eligible_blocks_after_release()`（`pressure.py:305`）已能算出单次释放新暴露的 Block；`_release_sort_key()`（`pressure.py:325`）是冻结 A0 顺序；压力循环在 `tier_1 ∪ tier_2` 达到 `target = min(required_blocks, queue_len)` 时停止。
- **假设（H3）**：按下游 victim 集合的期望增量损失排序 Entry 释放，能在满足容量目标的同时降低物理损失。
- **所需信号**：新暴露 Block 集合、下游 selector 的模拟结果、已验证的损失估计。
- **潜在收益**：避免"暴露很多 Block 但都是低代价 victim"与"暴露很少 Block 但含浅层共享块"被 deadline 一视同仁。
- **风险**：A0 顺序已消费 `native_lru_rank`，headroom 可能很小；A1 的 54/54 复现说明看似更丰富的排序很容易退化成简单规则；一次释放往往不足以满足容量目标，lookahead 单位定义不清会使比较失去意义。
- **验证方法**：固定下游 selector，只改 Entry 释放顺序；必报候选方法间的 pairwise ordering agreement 与 rank correlation；强制首释放（`diagnostic_first_release_program_id`）的运行必须排除或单独分层报告。
- **当前证据**：A1 的有界结果（54/54 可被简单启发式复现）是直接的反向警示。

### 4.4 Entry Idea 4 — 整 Entry 解除保护 vs 部分尾部解除保护

- **研究问题**：整个 Entry 解除保护与只解除尾部保护，哪种能在释放空间的同时保留有价值的浅层共享前缀？
- **已有机制**：`RetentionEntrySnapshot` 只有 `protected` 布尔量与 `block_ids` 元组，保护粒度是 Entry 级；`KVCacheManager.free()` 一次释放某请求的全部 Block，仓库内没有子请求粒度的释放能力。
- **假设（H4）**：在期望保留浅层前缀的代价低于暴露它的代价、且尾部 Block 足以满足容量目标时，优先释放尾部。
- **所需信号**：Block 范围/深度级的保护表示、共享所有权记账、逐出后可复用前缀长度。
- **潜在收益**：保留被多个未来请求复用的浅层前缀。
- **风险**：逻辑 Entry 边界不等于物理 Block 所有权边界；释放一个 Entry 的保护不能在另一 owner 仍保护该 Block 时使其可回收；部分 unpin 与部分物理驱逐不是同一件事；可能根本无法表示而非仅仅未被证明。
- **验证方法**：同一压力事件与下游 selector 下，整 Entry vs 固定尾长 vs 成本感知部分尾部；必须报告保留的可复用前缀长度、实际释放的物理 Block 数、以及共享所有权/前缀连续性/并发正确性检查。
- **当前证据**：无。该方向尚未被检验。

## 5. 范围边界（不做什么）

- 不改注意力内核；不做多卡与分布式；不做 CPU KV offloading；不复现 PagedAttention / vLLM 本身。
- 不复现 ARC、RLT/LBGR、SAGA 的完整系统；它们只作为机制对照与灵感来源。
- Continuum 风格基线复现其动态 TTL / retention 与程序级调度决策逻辑，**不复现其完整系统**，也不声称与论文逐行等价。
- 尚未冻结的评分函数、信号权重、介入阈值与 partial-tail 规则，一律保持 proposal / hypothesis 定位。
- 完整排除清单见 [`docs/baseline-freeze.md`](../baseline-freeze.md) 的 Explicit First-Version Exclusions。
